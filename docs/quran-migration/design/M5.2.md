# M5.2 design: the Library (the Quran tab's root)

**Changed after the first UI test run (2026-10-11), before commit.** (1) **Continue reading is pinned under the header**, outside the scrolling indexes (`QuranLibraryContinueBar`, placed by `QuranLibraryContent`). As first designed (3.5, Batch 4) it was the first row *inside* each index. A UI test that scrolled to surah 18, opened it and came back could not find the row, and it was right: the list keeps its scroll position, so the row was off the top, and on the Page tab the grid scrolls itself to the current page on appear, so a row above it was almost never on screen. A row that exists to give the reader a way back must not be hidden by default. It is shown when there is a place to return to and the field is not narrowing the surah list. The three list views no longer take `resume:`; the grid takes `currentPage:` for its mark and its scroll. Where sections 3.5, 5 and Batch 4 below still describe an in-list row, read them as superseded by this. (2) **A failed submit keeps the field focused**, so the reader can correct what they typed; Return used to dismiss the keyboard and leave the error beside an unfocused field. (3) Two build fixes by the main agent: a missing space in `AppContainer`, and the partial-address regex in `QuranGoTo` given extended delimiters (`#/…/#`), because a bare-slash literal ending in `*/` reads as the end of a block comment. (4) One new Arabic string was reworded on review: "No surah matches that." is `لا توجد سورة مطابقة.`, not a phrase with the word *search*, since the field is deliberately not search.

Status of the facts used here. Everything about this repo (HEAD `006b81f`) and the Mushaf reference was read from the files named, and the `migration-scout` inventory of Mushaf's Library folder was checked against them. Everything about how SwiftUI *behaves* at run time (`.contentMargins` on a `List`, a `Button` as a `DisclosureGroup` label, `.textSelection` over a column of `Text`, italics in IBM Plex) is marked **unverified** where it is, and section 7 gives the check and the fallback for each. Nothing was built or run for this note.

## 1. Goal and scope

**Goal.** `QuranLibraryView` grows from M5.1's surah index into Mushaf's Library: one field that goes to an address and filters the surahs, over Surah / Juz / Hizb / Page indexes, with surah info where its pack is bundled.
The public (Tanzil) build shows three tabs and no page number anywhere, decided in one place (Q5).

### What M5.2 delivers

| Piece | Delivered now |
|---|---|
| Indexes | Surah, Juz, Hizb (with its three later quarters), Page grid. Page exists only where the corpus has pages. |
| The field | Mushaf's go-to grammar and surah filter in one `TextField`, with its hint, its error line and a typed refusal for a page in the public build. |
| Rows | Number, names, revelation place, ayah count, the QUL name glyph where the face registered, start page where the build has pages. |
| Surah info | `QuranRoute.surahInfo(Int)`, a pushed screen. Offered only where a surah-info pack exists in the interface language. |
| The tafsir HTML renderer | `TafsirDocument`, `TafsirStyling`, `TafsirTextView`: **pulled forward from M5.3**, because surah info is their first caller (decision 3). M5.3 uses them as built. |
| Continue reading | A **session-only** row (decision 1, section 3.5). |
| DEBUG | `-quranLibrary surah|juz|hizb|page`; reader settings from the launch options are now seeded before any Quran object exists (4.5). |

### The two owner texts on Continue reading, and the ruling

The milestone prompt says "Continue reading appears in M6"; the task table lists a "Continue reading row" under M5.2. `MAPPING.md` 1.6 and section 6 side with the first; M5.1's note sides with the second. Mushaf's own Library has no such row (its only sign of the reader's place is the highlighted cell on the Page tab).

**Ruling: M5.2 ships the row, backed by the place the reader already keeps in memory. M6 adds what makes it survive a relaunch, and Home's card.** Read that way both texts hold: the *row* is M5.2's, the *feature a reader would call "continue reading"* (it is there when the app is opened tomorrow) appears in M6.

Reasons:

- M5.1 opened a hole and this closes it. The reader's Library button is `popToRoot()`, and from the root every row is an explicit target, so today a look at the index costs the reader their place. That is felt on the first device test, not only in M6.
- It meets "a control appears only once it works". The row is drawn only when there is a place to return to (the reader has been shown in this process) and its action, `QuranCoordinator.openReader()`, was written in M5.1 for exactly this. Before that it is absent, not disabled, which is the rule Hadith's own continue row follows.
- Nothing is thrown away at M6: the row view stays, and its *source* changes from the live view model to the restored `ReadingPosition`.
- The cost of being wrong is small in both directions. No build between M5.2 and M6 reaches a user (the branch merges after M8), so nobody outside meets a row that forgets overnight.

What it does not do, stated: after a relaunch there is no row until the reader is opened once. **This is decision 1 for Saad; removing the row is deleting one view and two lines.**

### Out of scope

- The ayah panel, context menu, copy/share (M5.3). `TafsirSection`, `TafsirReaderView`, `TafsirChoice` and the tafsir repository's callers stay M5.3's; only the document, its styling and its text view come forward.
- Separated mode's content, Next surah, the surah header's own "Surah Info" menu (`surahInfoMenu`, four reader files in Mushaf): M5.4.
- Search (M5.5). **The line:** the Library's field navigates by *address* (a number, `s:a`, a division) and narrows the 114 *names* already in memory. It never reads ayah text and never touches FTS. M5.5 reads text through `QuranSearchRepositoring` and owns `.searchable` or `QuranRoute.search`; the Library uses a plain `TextField` so the two cannot be mistaken for each other. M5.5's "surah names" scope overlaps the filter on purpose (Mushaf has both).
- Reader settings and the Settings section (M5.6). Bookmarks, `ReadingPosition`, `RecentActivity`, Home's continue-reading card (M6).
- Mushaf's "Open in New Window" context-menu entry (windows are dropped with D3), its Cancel button (the Library is no longer a sheet), `DeepLink.quranPage` (M7).
- Any change to the reader screen, the pager, `QuranReaderViewModel`, `QuranReaderPlace`, `GoToTarget`, `SurahNameGlyph`, `QuranReaderSettings`.

**What crosses an isolation boundary.**

1. `QuranLibraryIndex.make(from:)`: takes a `QuranCorpus` (`Sendable`), returns a `QuranLibraryIndex` (`Sendable`). `@concurrent`, so it leaves the main actor the same way the repository's methods do.
2. `TafsirDocument.parsed(html:)`: takes a `String`, returns a `TafsirDocument`. `@concurrent`.
3. `SurahInfoRepositoring` (an actor behind a `Sendable` protocol, M3): `pack(for:)` and `info(surah:pack:)` return `Sendable` values.

Nothing else. No `Task.detached`, no new actor, no stored `Task`: every call above is awaited from a view's `.task`, and none of them is cancellation-aware, so a task cancelled half-way still finishes its step and the next `.task` finds the work done or repeats an idempotent call.

**T13, the one departure from "port the annotation verbatim".** Mushaf parsed with `Task.detached(priority: .userInitiated)`. Here it is a `@concurrent` function: the same hop, but structured (it inherits the caller's priority and is not a second unowned task), and it is the mechanism this repo already uses for the corpus load. The comment on `parsed(html:)` says why it leaves the main actor: a surah's introduction is tens of kilobytes of HTML walked character by character, and this module's default isolation would otherwise run that on the main actor in the middle of a push animation.

## 3. Data flow

### 3.1 Who owns what

| Value | Owner | Kind | Persisted |
|---|---|---|---|
| The corpus and its load phase | `QuranReaderViewModel` (M5.1) | session | no |
| The index: every row model, and whether this build shows pages | `QuranLibraryViewModel`, built once from the corpus | session | no |
| The selected tab | `QuranLibraryViewModel` (stores the request, exposes the resolved tab) | session | **no** (below) |
| The field's text, the filtered surahs, the go-to failure | `QuranLibraryViewModel` | session | no |
| Whether surah info exists here; the introduction being read | `SurahInfoViewModel` | session | no |
| Which screens are pushed, including surah info | `QuranCoordinator.path` | navigation | no |
| "The reader has been shown in this process" | `QuranCoordinator.hasShownReader` | navigation | no (M6 replaces it) |
| Where Continue reading returns to | derived on demand from `QuranReaderViewModel` (3.5) | session | no (M6) |
| Faces | `AppContainer.quranFaces`, put in the environment on the section's stack | launch | |

`QuranLibraryViewModel` is a `let` on `AppContainer`, built after `quranReaderViewModel` and before any view. It lives outside the view tree for the reason every other section's state does: an iPad crossing compact and regular rebuilds the arrangement, and the tab, the text typed so far and the error must still be there.

**Nothing is written to `SettingsStore` by this task.** The selected tab is the one candidate, and it stays in memory:

- Mushaf did not remember it (plain `@State`), and the port keeps its behaviour.
- The tab changes without the reader choosing it: typing a name moves to Surah. A key written there would break "only write a key the user chose", and a key written only on a tap of the picker would disagree with what was on screen at the last quit.
- A stored `page` would name a tab the public build does not have.

So the tab is `.surah` at launch and survives everything short of a relaunch. Reversible: one key and two lines if Saad wants it remembered.

No view touches GRDB, SwiftData or the file system. The two view models see Domain protocols and the reader's view model.

### 3.2 The index: built once, off the main actor

**No query is needed.** Everything the four indexes show is already on the loaded `QuranCorpus`: `surahs`, `metadata.juz`, `metadata.hizb`, `metadata.rub`, `pages`. The reads that produced them ran inside `QuranRepositoring.loadCorpus`, which is `@concurrent`. What is left is turning them into row models, and that is done once:

- 114 surah rows, each with two **folded search keys** (Latin letters only; Arabic through `ArabicNormalizer`), so a keystroke folds the query and runs 114 `contains`, never 114 normalisations;
- 30 juz rows, 60 hizb rows each holding its three later quarters (from `rub`, grouped in one pass);
- 604 page cells in a full build (each needs the page's first ayah, a walk over its lines), none in the public build.

`QuranLibraryViewModel.load(language:)`, in this order: `await reader.load()`; return if there is no corpus or the index exists; `await surahInfo.prepare(language:)`; `let index = await QuranLibraryIndex.make(from: corpus)`; store it if there is still none, and run the filter once. Every step is idempotent, so two callers at once are safe. The phase the view switches on is derived: the reader's `.loading` and `.failed` as they are, and `.ready(index)` only when the index exists. **Surah info availability is resolved before the index is published**, so the first frame that has rows already knows whether a row offers it.

**Who calls it.** Two places, deliberately. The section's `NavigationStack` (`AppSectionView.quran`) runs it in a `.task`, and so does `QuranLibraryView`. The first is what matters when the *reader* is the first screen of the session (a verse link from Home, a scripted launch): the index is then built while the reader is in front, and the root's first frame, when the reader is popped, already has its rows. Had only the root's own `.task` built it, that first reveal would have shown a spinner for a few frames. The second keeps the root working on its own (a preview, a test host).

Per keystroke: `query`'s `didSet` (the pattern `NamesViewModel` uses) classifies the text, clears the failure, stores `filteredSurahs` and, for a name, selects the Surah tab. `filteredSurahs` is stored, not computed, so the list does not re-filter per redraw. No debounce: the filter is 114 string searches in memory, and a delay would only make the list lag the typing. (The Hadith and Quran text searches debounce because they hit SQLite.)

### 3.3 Capability checks, in one place

**`QuranLibraryIndex` is the place.** It is built from the corpus the reader will draw, and it answers both questions:

```swift
/// Which indexes a build shows. Q5: no Page tab where there are no printed pages.
static func tabs(showingPages: Bool) -> [QuranLibraryTab]   // [.surah, .juz, .hizb] + (.page if true)
let showsPages: Bool                                         // corpus.hasPages, read once in init
var tabs: [QuranLibraryTab] { Self.tabs(showingPages: showsPages) }
```

- **Which tabs:** the picker iterates `viewModel.visibleTabs` (`index.tabs`). `viewModel.tab` is *resolved*: the stored request if `visibleTabs` contains it, else `.surah`. That is `QuranReaderSettings.displayMode`'s shape (a choice, and what this build can show of it), so a request made before the corpus loaded (a launch option) is judged when it has.
- **Does a row carry a page:** every `page` in every row model goes through one private function in `QuranLibraryIndex.init`, `showsPages ? value : nil`. The views draw a page only when the row has one. So the public build shows no page number even if a future public database were to carry Tanzil's page table: the gate is the build's capability, not the column happening to be empty.
- **Go-to validation:** `QuranGoTo.resolve(_:corpus:index:)` reads `index.showsPages` (3.4).
- **Launch options:** `-quranLibrary page` sets the *request*; the resolved tab is Surah in the public build, by the same getter.
- **Tests:** assert on `QuranLibraryIndex(corpus:)` for both databases.

`corpus.hasPages` and `QuranCapabilities.supportsMushafPages` are already pinned equal for both databases by M5.1's tests, and `corpus.hasPages` is the condition the reading surface switches on, so the Library, the reader and the settings gate cannot disagree. Nothing checks which file was bundled.

Surah info is **not** a database capability and is not folded into this: it depends on a *pack* and on the interface language (3.6). `-quranData public` on a machine with the full data shows exactly that: three tabs, no pages, and surah info still offered.

### 3.4 The go-to field

One field does both jobs, as in Mushaf. Ported behaviour, then the three places Noor differs and why.

**What is accepted** (all from `Domain/GoToTarget.swift`, ported in M3 and not edited; it kept every word, the optional dot and the digit systems of Mushaf's file):

| Typed | Means | Notes |
|---|---|---|
| `2:255`, `2/255`, `2 255`, `٢:٢٥٥` | ayah 2:255 | `VerseReference(parsing:)`: separators `:`, `/`, space; ASCII, Arabic-Indic and Extended Arabic-Indic digits. |
| `juz 5`, `Juz. 5`, `j5`, `ج ٥`, `جزء ٥`, `الجزء ٥` | juz 5 | Words: `juz, juz', juzʼ, j, ج, جزء, الجزء`. An optional dot after the word; the space is optional. |
| `hizb 12`, `h12`, `ح ١٢`, `حزب ١٢`, `الحزب ١٢` | hizb 12 | `hizb, h, ح, حزب, الحزب` |
| `surah 18`, `sura 18`, `s18`, `س ١٨`, `سورة ١٨`, `السورة ١٨` | surah 18 | |
| `page 50`, `p50`, `ص ٥٠`, `صفحة ٥٠`, `الصفحة ٥٠` | page 50 | **Full build only.** |
| a bare number, `50`, `٥٠` | **full build:** page 50. **Public build:** surah 50 (see below). | |
| anything else | a surah name to filter by | |

The words are matched input, so they stay literals (MAPPING 1.5); ranges come from the loaded corpus, never from a literal.

**While typing.** Nothing is parsed into a target and nothing on screen claims one (Mushaf's behaviour). The Surah list narrows to the surahs whose number, English name (ASCII letters, case-insensitive: "imran" finds Ali 'Imran) or Arabic name (folded: hamza forms, tashkeel) matches. The other three indexes are not filtered. Under the field is the example line, "For example: 50, 2:255, juz 5, hizb 12", its numbers through `LocalizationManager` and `2:255` passed as **one** argument (each argument is bidi-isolated, so two would swap around the colon in Arabic). In the public build the first example is `18`, because there it is a surah.

**Submit** (the keyboard's Go, or the Go button, enabled when the trimmed text is not empty). `QuranGoTo.resolve`, a pure function:

1. In a build without pages, text that names a page with its word (`page 50`, `ص ٥٠`, `p50`) is `.failed(.pagesUnavailable)`.
2. `GoToTarget.parse(text, in: corpus)` gives a target: `.go(target)`.
3. Otherwise, if the filter leaves exactly one surah: `.go(.surah(n))`.
4. Otherwise `.failed(.notFound)`.

On `.go` the view model clears the field and the view calls `coordinator.open(target)`. On a failure the text is kept, the example line is replaced by the message in `theme.danger` (Mushaf's literal `.red`), and it is announced to VoiceOver; the next edit clears it.

**Where Noor differs from Mushaf.**

1. **No Cancel; Go is in the field's row.** In Mushaf the Library is a sheet with Cancel and Go in its bar, and a go dismisses it. Here it is the tab's root: there is nothing to cancel, so the row has a clear button (shown while there is text) and a Go button. `.onSubmit` and `.submitLabel(.go)` cover the keyboard.
2. **The field is cleared when the Library opens something** (a successful submit, or a row). Mushaf's sheet was dismissed and came back empty; a root that kept `2:255` would greet the returning reader with a filter that matches nothing.
3. **An address being typed neither filters nor moves the tab.** In Mushaf, typing `juz 5` on the Juz tab jumps to Surah at the `j` and shows "No Results" over the surah list until submit (the scout's wart). Here `QuranGoToInput` classifies the text once:

   | Class | Text | Filter | Tab |
   |---|---|---|---|
   | `.empty` | nothing | all surahs | unchanged |
   | `.number(n)` | digits only | the surah with that number | unchanged |
   | `.address` | a complete `juz 5` / `2:255`, a number followed by `:` or `/`, or text that is still a prefix of one of the unit words (`j`, `ju`, `juz`, `ال`, `الج`) | **all surahs** | unchanged |
   | `.name` | anything else | by name | **moves to Surah** |

   The cost is a delay of a letter or two for a few names: `hijr` filters from its third letter, and Arabic names from the letter after `ال`. Mushaf's two other rules are unchanged: a number never moves the tab, and a name always does.

**A bare number in the public build is a surah number** (decision 2). The public build has no pages, so rule 2 finds nothing and rule 3 finds the one surah with that number, which is the row the filter is already showing. The placeholder there reads "Surah, surah:ayah, juz or hizb" and never offers a page. A page is refused *only* when the reader says "page". The alternative, refusing every bare number, would tell a reader who has never seen a page number in this app that `18` is not allowed while row 18 sits in front of them. No page number is ever mapped: `QuranGoTo.resolve` cannot return `.page` for an index without pages, and `QuranReaderPlace.resolve` returns `nil` for one regardless (M5.1).

**Inherited from Mushaf and kept:** in the full build `18` narrows the list to surah 18 while Go opens page 18. Porting exactly; noted for Saad under "Later" (a one-line preview of where Go leads would remove it).

### 3.5 Continue reading, and the current page on the Page tab

Both read the reader's *live* place, and M5.1's rule (3.4 there) is that such a read must never be tracked by a body that stays alive under the reader: the root is still in the stack while the reader is pushed, and a body that had read `mushaf.page` would be re-evaluated on every page turn.

The mechanism is the one M5.1 ended up with for the separated list: **an untracked value, read in a body that is guaranteed to run at the moment the value is wanted.**

- `QuranCoordinator.canContinueReading` is `hasShownReader && !path.contains(.reader)`. It is observed and changes at navigation rate.
- The ready view's body computes, once: `let resume = coordinator.canContinueReading ? viewModel.resume : nil`, and passes that *value* down.
- While the reader is on the path the condition is false, `viewModel.resume` is not read, and nothing about the reader's place is tracked. A page turn invalidates nothing in the Library.
- When the reader is popped the path changes, the body runs in the same update that reveals the root, and it reads the place current at that instant, including `separatedLocation`, which is deliberately unobserved. No `onAppear`, no `.task(id: path)`: either would land after the root's first frame, which is the fault M5.1 was reviewed for.

`viewModel.resume` is `QuranLibraryResume(surah:ayah:page:)`: `reader.location`; its surah; and the page, which is `reader.mushaf.page` while pages are showing and `corpus.pageNumber(for: location)` otherwise, and `nil` where the index shows no pages. (Not `pageNumber(for: location)` in Mushaf mode: the first ayah with words on a page may have *started* on the page before.)

The row is the first row of each list and the first element above the page grid, so it scrolls with the content and costs an iPhone SE nothing once the reader starts down the list. It is hidden while the surah list is being filtered. It reads "Continue Reading" (existing key), then the surah's name with `s:a`, then "Page N" where there is one. Tap: `coordinator.openReader()`.

The Page tab highlights `resume?.page` and scrolls it to the centre on appear, as Mushaf does with the current page.

### 3.6 Surah info

**Hidden exactly as Mushaf hid it.** Mushaf's `hasSurahInfo` is `pack(forLanguage: AppLanguage.current) != nil` (`ReaderRootView.swift:181`), the repository matches the language exactly, and only an English pack exists. So the affordance is absent in a public clone (no pack), and absent in an Arabic interface (no Arabic pack; `SurahInfoRepositoring.pack(for:)` already documents that the Arabic interface shows none rather than English text). Here: `SurahInfoViewModel.prepare(language:)` asks once and keeps the pack; `isAvailable` is `pack != nil`; the surah list adds its swipe action and context-menu item only when `viewModel.hasSurahInfo`. Absent, never disabled.

**Opened** from a surah row by a trailing swipe action and a context menu (long press, or right-click on the Mac), which is Mushaf's choice. Both call `coordinator.showSurahInfo(number)`.

**The screen.** `SurahInfoView(viewModel:surah:)`: a facts card (the name glyph at 44; Revelation; Ayahs; Pages as `start–last` when they differ, and **no Pages row where the corpus has no pages**; Starts in: Juz N), then the introduction, then the pack's name and author. App colours and `.appFont`: it is an app screen like the Library, not a page.

`SurahInfoViewModel.load(surah:)`: returns at once when the content on hand is already this surah's (so a rebuilt view tree does not reload); else `.loading`, `repository.info(surah:pack:)`, `await TafsirDocument.parsed(html:)` off the main actor, then `.loaded`, or `.missing` when the pack has no row. A result is applied only if this surah is still the one asked for.

**`.textSelection(.enabled)`** is applied where Mushaf applied it, on the `TafsirTextView` alone, inside a vertical `ScrollView`. `CLAUDE.md` records that a selectable `Text` reported its natural width on the adhkar card and collapsed the pager's pages. That was a horizontal paging scroll view sizing its pages from their content; here every block is framed to the column's width in a vertical scroll view, the layout Mushaf shipped. **Unverified in this app:** check 3 in section 7, and the fallback is deleting the one modifier.

**The text size** is `@ScaledMetric(relativeTo: .body)` seeded with Mushaf's 17, handed to `TafsirTextView` as an already-scaled size, which the styling turns into `fixedSize` fonts. That is the rule `CLAUDE.md` gives for a size that has already been multiplied.

## 4. Navigation

### 4.1 `QuranRoute`

`.surahInfo(Int)` is declared now, because its destination becomes real now (M5.1's rule). `.search`, `.tafsir`, `.bookmarks` stay undeclared.

`QuranCoordinator` gains:

```swift
/// The reader has been pushed at least once in this process, so there is a place to go back to.
/// In memory: M6 replaces it with the restored `ReadingPosition`.
private(set) var hasShownReader = false          // set in showReader()

/// Continue reading can be offered: there is a place, and the reader is not already on the stack.
var canContinueReading: Bool { hasShownReader && !path.contains(.reader) }

/// Pushes a surah's introduction, unless it is already the screen in front.
func showSurahInfo(_ surah: Int)                 // if path.last != .surahInfo(surah) { path.append(.surahInfo(surah)) }
```

**M5.1's invariant holds:** at most one reader, and when there is one it is `path[0]`. From the Library the path becomes `[.surahInfo(n)]`; a later task that offers surah info from the reader gets `[.reader, .surahInfo(n)]` from the same function. `open(_:)` from `[.surahInfo(n)]` replaces the stack with the reader, as M5.1 wrote it.

### 4.2 Surah info is a push, not Mushaf's sheet

- M5.1 reserved the route case for this.
- In Noor a push is "a visit that ends by going back", which is what reading one surah's introduction is, and the path is already outside the view tree, so it survives an iPad changing arrangement with no extra state.
- It is long prose (several screens for the long surahs). A pushed screen gives it the whole detail column; a sheet on the Mac is a fixed, modal box.
- The reader will want the same screen from a surah header (M5.4). A route serves both; a sheet would need presentation state in two places.

So there is no Done button: Back returns to the Library with its tab, its scroll position and (since nothing was opened) its filter intact.

### 4.3 What a tap opens

| Row | Call | Lands (M5.1's `QuranReaderPlace`) |
|---|---|---|
| Surah | `coordinator.open(.surah(n))` | `n:1`; its start page in Mushaf mode. |
| Juz | `coordinator.open(.juz(n))` | The juz's start ayah. **Q4:** in separated mode that is the start ayah's surah, at that ayah. |
| Hizb | `coordinator.open(.hizb(n))` | The same, for the hizb. |
| Quarter | `coordinator.open(.ayah(start))` | The quarter's start ayah, selected (Mushaf sends a quarter to its ayah, not to its hizb). |
| Page cell | `coordinator.open(.page(n))` | Page `n`. The cell exists only where the index shows pages, so a `.page` target is never produced in the public build. |
| Continue reading | `coordinator.openReader()` | Where the reader was left, in the mode it was left in. |
| Go | `coordinator.open(target)` | As above. |

Every one of these first calls `viewModel.didOpen()` (clears the field). Each row's `target` is on its row model, built once.

### 4.4 `AppRoute`, `DeepLink`, back and restore

**No change to `AppRoute` or `DeepLink`.** `AppRoute.quran` is still `popToRoot()`, which now also pops a surah-info screen: the route means "the Quran tab, at its Library". `.quranVerse` is unchanged.

| Event | Preserved | Not preserved |
|---|---|---|
| Leaving the tab and returning | Tab, text, failure, scroll position, any pushed screen. | |
| iPad crossing compact/regular | Tab, text, failure, the path. | Scroll position of the index (the list is rebuilt at its top; the Page grid re-centres on the current page). |
| Back from the reader | Tab. Continue reading now names where the reader was. | The text: it was cleared when the reader was opened. |
| Back from surah info | Everything. | |
| Relaunch | Nothing of the Library: Surah tab, empty field, no Continue reading row until the reader is opened. | By design until M6. |

### 4.5 `QuranLaunchOptions`

One new option, DEBUG only: **`-quranLibrary surah|juz|hizb|page`**. Mushaf had `-debugLibrary` for the same reason: without it every Library test and capture launches into the reader, taps Library, then taps the picker.

- A launch that names it (or a reader target) starts past onboarding on the Quran tab: `isQuranLaunch`. With `-quranLibrary` alone the path stays empty; with a reader target too, the reader is pushed over a Library already on that tab.
- The tab is set on the view model in `AppContainer.init`, as a *request*. `page` in the public build resolves to Surah by the same getter the picker uses. No view consumes it.
- **No option for the field's text.** Typing it is the flow under test, and a second way to fill the field is a second thing to keep honest.

**The reader's settings options, for a launch that never shows the reader first.** `launchQuran` always passes `-quranResetSettings YES -quranFollowSystem NO`, and M5.1 applies those in a hook attached to the *reader* destination. A Library launch has no reader on screen, so nothing would reset the store, and the reader opened by the first tap would inherit the previous run's mode and theme. Moving the hook to the root would apply them a turn after the load: M5.1's fault again, in a new place.

So they are written **before the settings object exists**: in `AppContainer.init`, immediately before `QuranReaderSettings(settingsStore:)`, the options are applied to a throwaway `QuranReaderSettings` over the same store, built with `capabilities: [.text, .mushafPages]`. The key mapping stays in one type; `-quranMode mushaf` is stored like a reader's choice; and the real object, constructed on the next line, reads it and judges it against what the database turns out to carry, by the product's own code path. `QuranLaunchHooks.swift` is not edited: for a reader target it still re-applies after the load, which is now a harmless repeat.

## 5. Layout on each arrangement

One view, no `#if os`, no size-class branch.

```
NavigationStack                      (AppSectionView, unchanged seam)
└─ QuranLibraryView                  title "Quran", inline
   ├─ loading / failed               ProgressView / QuranLoadFailureView (M5.1's)
   └─ ready: VStack(spacing: 0)
      ├─ QuranLibraryHeader          pinned: field row, hint or error, segmented picker
      └─ one of four indexes         the only scrolling part
```

- **The title is inline.** The header is pinned above the scroll view, and a large title only collapses over a scroll view that starts at the top of the screen; with a header in between it would sit there permanently, a third of an iPhone SE.
- **The header is pinned**, not the list's first row: the four indexes are four scroll views, and a field that lived inside one would lose its focus and its text field every time the tab changed.
- **Width.** The only thing that changes with width is side margin and the number of grid columns:
  - the header's content and the three lists are held to `AppBreakpoint.readingMeasure` (640), centred. The lists do it with `.contentMargins(.horizontal, …, for: .scrollContent)` computed from their own measured width, so the *scroll view* stays full width and a drag or a scroll wheel anywhere in the column still scrolls it (a narrowed `List` would only scroll from inside itself). **Unverified** that a `List` honours `contentMargins` at iOS 17: check 4; the fallback is to delete the modifier and accept full-width rows, which is how a list in a detail column usually looks.
  - the page grid fills the width with `GridItem(.adaptive(minimum: 76))`: it is a table of cells, and more columns mean less scrolling through 604 of them.
  - `AppBreakpoint` gains nothing.
- **iPhone:** below 640 the margins are zero; everything is full width.
- **iPad, sidebar arrangement:** the Library is the detail column's root. It is a list in a detail column, not a second sidebar; the split view stays two columns.
- **Mac:** the same view. The context menu is the right-click; the swipe action works from a trackpad; Return in the field submits.
- **Dynamic Type.** At an accessibility size the four-way segmented picker cannot hold its labels, so the picker switches to `.menu` style (`dynamicTypeSize.isAccessibilitySize`), and a row's trailing column (glyph and page) moves under its name with `AnyLayout`. Both are one condition in one view each, not a second layout.
- **Colours and type:** `theme.background`, `theme.surface` for rows, `theme.textPrimary` / `textSecondary`, `theme.accent` for the number, `theme.danger` for the failure; `.appFont` throughout. The one fixed-size face is `SurahNameGlyph`'s, which is M4's documented exception. No page palette: this is an app screen.

nonisolated enum QuranGoToInput: Equatable, Sendable {
    case empty
    /// Digits only, in any of the three digit systems.
    case number(Int)
    /// A complete address ("juz 5", "2:255"), or text that can still become one.
    case address
    /// Anything else: a surah name to filter by.
    case name
    init(_ text: String)
}

    case notFound
    /// A page was asked of a build that has no printed pages.
    case pagesUnavailable
}

nonisolated enum QuranGoToOutcome: Equatable, Sendable {
    case go(GoToTarget)
    case failed(QuranGoToFailure)
}

nonisolated enum QuranGoTo {
    static func resolve(_ text: String, corpus: QuranCorpus, index: QuranLibraryIndex) -> QuranGoToOutcome
    static func surahs(_ rows: [QuranLibrarySurahRow], matching text: String) -> [QuranLibrarySurahRow]
    static func latinKey(_ text: String) -> String     // lower-cased, ASCII letters only
    static func arabicKey(_ text: String) -> String    // ArabicNormalizer.words(in:).joined()
}

## 8. Risks

**The plan's traps.**

- **T4 (two builds).** One type decides what the Library shows, built from the corpus the reader draws. The public build has three tabs, no page on any row, no page cell, a typed "page 50" refused with its own message, and a `.page` target that cannot be constructed. `-quranData public` exercises all of it where the full data is bundled, with M5.1's stated limit: packs and faces are still the bundle's, so that launch shows surah info and the name glyphs. A public *clone* remains the real check (M5.7).
- **T10 (strings).** Twenty-two literals, seventeen with Mushaf's Arabic, eleven existing keys reused. Every number in a format string is formatted by `LocalizationManager` first and passed as a string; `2:255` is one argument so bidi cannot split it. The typed keywords stay literals, as MAPPING rules.
- **T15 (packs are found, not listed).** Surah info asks `SurahInfoRepositoring.pack(for:)`, which asks the store, which scans. Nothing here names a pack id or a file, so a build with a different set of packs needs no code.
- **T13 (isolation).** Two `@concurrent` functions and an existing actor are the only work off the main actor, each returning a `Sendable` value. Mushaf's detached parse became a structured one, on purpose (section 2).
- **T7, T11.** Not moved: no `AppRoute` or `DeepLink` change; the Library adds nothing to the reader's chrome and gives the pager no size.
- **T16, T17, T1.** Not in play: no tafsir entry is fetched (the document type is only a parser); no text search; no page fonts.

**M5.1's lesson: what a view needs at its first frame is applied before the view exists.** Five places it could have been repeated, and what the design does instead:

- *The launch's tab* is set on the view model in `AppContainer.init`, as a request the resolved getter judges later. No view consumes it.
- *The launch's reader settings* are written to the store before the settings object is constructed (4.5).
- *The index* is built from the section's stack, so it exists before the root is first revealed when the reader came first (3.2).
- *Surah info availability* is resolved before the index is published, so no row appears without knowing.
- *Continue reading's place* is read in the body that the pop itself re-evaluates, not in `onAppear` or a `.task` after it.

One place still acts after the first frame, knowingly: the Page grid's `scrollTo` in `onAppear`, which is Mushaf's code and has a check (6).

**Traps of this task's own.**

- **A hidden root that works on every page turn.** The root stays alive under the reader. Avoided by 3.5 and held by the reviewer's second check and verification 2.
- **A page number meaning two things.** Avoided structurally (T4 above). The one judgement call, a bare number in the public build, is decision 2.
- **`ContentUnavailableView` over a list that is not empty by the reader's doing.** Mushaf showed "No Results" while "juz 5" was being typed. Avoided by `QuranGoToInput`, tested.
- **A field that outlives its use.** A root keeps its text where a sheet did not. Cleared on every open.
- **Two faults in one glyph.** In a public clone `SurahNameGlyph` falls back to a name; passing the interface-language name would print "Al-Kahf" twice in one row. It is passed the Arabic name and left out where the row already shows it.
- **The Arabic interface and surah info.** Absent, as in Mushaf. A reader who switches the interface to Arabic loses the affordance; that is the existing ruling on `SurahInfoRepositoring.pack(for:)`, not new.
- **Dynamic Type.** Four segments do not fit at an accessibility size; the picker becomes a menu there.
- **UI tests:** the tip popover, the orientation and the software keyboard, each named in section 7.
- **Unverified SwiftUI behaviour:** `contentMargins` on `List`, the hizb disclosure, `.textSelection`, italics. Each has a check and a fallback that is a deletion, except the disclosure, whose fallback is Saad's call.
- **Scope.** The tafsir renderer arrives one task early. It is a leaf (no file outside Batches 5 and 6 names it), M5.3 is told it exists, and decision 3 is the way to send it back.

**The item M5.0 left on file.** `DeepLinkInbox.makeCurrent` timing: not touched. `AppContainer.init` gains two stored properties that read no disk and two DEBUG statements, none of them before `makeCurrent`.
