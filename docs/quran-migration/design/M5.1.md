**Changed after review (2026-10-11), before commit.** Two faults in how the reader kept its place were found by the reviewer reading the code; no test reached them. (1) The coordinator's one-shot `pendingTarget`, consumed by the view after its first body pass, is gone: `open(_:)` now applies the target to the view model *before* it changes the path (4.3). (2) The content subview now reads the display mode, so a switch to separated inside one surah re-reads the place (3.4). Sections 3.1, 3.4, 4.2, 4.3 and the Batch 1 interface are corrected in place; anywhere else this note still says `pendingTarget` or `consumeTarget` (the launch-hook paragraph in 4.8, the reader's `body` order in Batch 3, the test lists in section 7), read it as superseded by 4.3: the coordinator tests assert the place on the view model instead, and the view-model tests gained the two cases that would have caught these. Also added: a VoiceOver escape action on the reader, since hiding the system back button removes the two-finger scrub.

Status of the facts used here. Everything about this repo and the Mushaf reference was read from the files named. Everything about how UIKit and SwiftUI *behave* at run time (bar colours under iOS 26 glass, the status bar inside a tab, the edge swipe against the pager) is marked **unverified** where it is, and section 7 lists the check and the fallback for each. ## 1. Goal and scope

**Goal.** The Quran tab runs on the ported engine through real navigation: a typed path on `QuranCoordinator`, a reader screen that hosts `QuranReadingSurface` in both modes with Mushaf's location-preserving switch, bars that take the page's colours inside the reader only (Q3), and iPhone immersive reading that also hides the tab bar (T11).
`AppRoute.quran` and `.quranVerse` land in the right place; the debug reader and the placeholder are gone; `QuranLaunchOptions` keeps driving scripted launches, DEBUG only.

### What M5.1 delivers

| Piece | Delivered now |
|---|---|
| `QuranRoute`, `QuranCoordinator` | The path, `open(_:)`, `popToRoot()`, the one-shot reader target. |
| `QuranReaderViewModel` | One per app: the corpus load, the reading place in both modes, target resolution, the mode switch, the immersive question. |

| DEBUG | `QuranLaunchOptions` reaches the real reader through `QuranLaunchHooks`; `QuranDebugReaderView`, `QuranDebugTarget` and `QuranPlaceholderView` are deleted. |

### The tab's root between M5.1 and M5.2

**`QuranLibraryView`, in `Features/Quran/Library/`, showing the surah index and nothing else.** Reasons:

- It is real and usable in both data builds: surahs exist in both, and a row opens the reader at that surah in whichever mode the build allows.
- It is the type and the file M5.2 owns. M5.2 replaces its *body* (Surah / Juz / Hizb / Page, the go-to field, Continue reading); the seam around it does not move: `AppSectionView.quran` builds `NavigationStack(path:) { QuranLibraryView(viewModel:coordinator:) }` today and after M5.2.
- The alternatives were worse. The reader as the root (Mushaf's shape) would have to be turned inside out in M5.2. Keeping the placeholder with a "start reading" button is a screen written to be thrown away.

It has no resume affordance: after going back, a row opens its surah at the top. "Continue reading" is M5.2's row and M6's persistence. Stated, not hidden.

**What crosses an isolation boundary.** One thing: the corpus load. `QuranReaderViewModel.load()` awaits `repository.capabilities()` and `repository.loadCorpus(style:)`, both `@concurrent`, and receives `QuranCapabilities` and `QuranCorpus`, both `nonisolated … Sendable`. The repository existential is `any QuranRepositoring`, which is `Sendable`. Nothing else leaves the main actor in this task: page fonts and measurement stay where M4 put them (`MushafPagerView.prepare(around:)`, `FontPackStore`, `PageMetricsCache`), untouched.

**T13, concretely.** No `Task.detached`, no `nonisolated` method on the view model, no new actor. The repository protocol's `@concurrent` is what moves the hundred-thousand-row read off the main actor, exactly as in Mushaf; wrapping the call in something else would be a second mechanism for one hop. `QuranReaderPlace.resolve` is pure and cheap (array index lookups) and runs on the main actor.

## 3. Data flow

### 3.1 Who owns what

| Value | Owner | Where it comes from |
|---|---|---|
| The path `[QuranRoute]` | `QuranCoordinator` (`AppContainer.quranCoordinator`) | Navigation calls. |
| A reader target | none: `QuranCoordinator.open(_:)` hands it straight to `QuranReaderViewModel.open(_:)`, which parks it until the corpus is loaded | applied before the path changes |
| The corpus and the load phase | `QuranReaderViewModel` (`AppContainer.quranReaderViewModel`, a `let`) | `quranRepository`, once per process. |
| What the build can draw | `QuranReaderSettings.capabilities` | `repository.capabilities()`, applied in **one** place: `QuranReaderViewModel.load()`. |
| The Mushaf page, the selected ayah, the "chrome hidden" request | `MushafReadingState` (M4), one instance owned by the view model | The pager writes the page and the chrome request; the view model writes on navigation. |
| The surah separated mode shows | `QuranReaderViewModel.separatedSurah` | Navigation only. |
| The first ayah in view in separated mode | `QuranReaderViewModel.separatedLocation`, **not observed** | The separated list, as it scrolls. |
| Display mode, theme, keep-awake, the rest | `QuranReaderSettings` over `SettingsStore` | Unchanged from M4. This task writes exactly one key, `quranDisplayMode`, and only when the reader presses the toggle. |
| Faces, render services | `AppContainer.quranFaces`, `.mushafRenderServices` | Passed into `QuranReaderView` by `AppSectionView`. |

No view touches GRDB, SwiftData or the file system. The view model sees a Domain protocol.

### 3.2 `QuranReaderViewModel`

**One instance for the section**, built in `AppContainer.init` beside `quranReaderSettings` (it touches no disk until `load()`), shared by the root and the reader as `HadithViewModel` is shared by that tab's screens. That is what makes the corpus load once and what keeps the reading place alive when the view tree is rebuilt.

**Load.** `load()` returns at once when the phase is `.ready`. Otherwise it starts, or joins, one stored `Task` that runs `capabilities()` then `loadCorpus(style:)`, and on success: `settings.apply(capabilities)`, `phase = .ready(corpus)`, then the parked target if there is one. On failure: the task is dropped and `phase = .failed`; `retry()` sets `.loading` and calls `load()`.

The stored task is deliberate, and it is the only unstructured task in this design. The root and the reader both call `load()` from `.task`. A load that belonged to one view's task would end with that view: the repository reads through GRDB's async `read` (four of them in `loadCorpus`), which GRDB 7 documents as honouring task cancellation (not re-verified here), so a reader popped or a tab switched half a second in would leave the phase at `.failed` for a reader who did nothing wrong. The load belongs to the session, so the session holds it. It is never cancelled: it is the one read the whole section needs.

**Cancellation on a target change.** A target never starts a load, so there is nothing of the view model's to cancel. A target that arrives while the corpus is loading is *parked* (the latest wins) and applied on arrival, which is Mushaf's `pendingTarget`. What a target change does cancel is the pager's own work: `open(_:)` calls `mushaf.show(page:)`, `state.page` changes, and SwiftUI cancels and restarts `MushafPagerView`'s `.task(id: state.page)` (font window and neighbour measurement). That mechanism is M4's and is not edited.

**The capability check, in one place.** `QuranReaderSettings` already is that place: `availableDisplayModes` and `displayMode` are gated on `capabilities`. This task feeds it from exactly one call site (`load()`), and asks two derived questions and no others:

- `viewModel.canSwitchDisplayMode` (`settings.availableDisplayModes.count > 1`): whether the toggle exists.
- `viewModel.showsMushafPages` (`settings.displayMode == .mushaf && corpus.hasPages`): what is on screen. It is the same condition `QuranReadingSurface` switches on, so the view model and the surface cannot disagree.

Nothing checks which file was bundled. A unit test pins `capabilities.supportsMushafPages == corpus.hasPages` for both databases.

### 3.3 The reading place, and the mode switch (Mushaf's rule, ported)

A target is a **`GoToTarget`** (already in Domain: `.page`, `.ayah`, `.surah`, `.juz`, `.hizb`). It is what the Library's rows and go-to field produce, what a search result is, and what `.quranVerse` becomes. It is resolved against the loaded corpus by `QuranReaderPlace.resolve(_:in:)` into **an ayah and, where the build has pages, a page**, so one target positions both modes at once (Mushaf's `ReaderModel.go(to:)`):

| Target | Ayah | Page | Selects the ayah |
|---|---|---|---|
| `.page(n)` | the page's `firstAyah` | `n` | no |
| `.ayah(ref)` | `ref` | `corpus.pageNumber(for: ref)` | yes |
| `.surah(n)` | `n:1` | `surah.startPage` | no |
| `.juz(n)`, `.hizb(n)` | the division's start ayah | the division's start page | no |

`nil`, and the reader stays where it is, when the target is not in the corpus: an ayah past the end of its surah, a surah 115, and **every `.page` in the Tanzil build** (it has no pages; a Tanzil page number is not a V2 page number, MAPPING T4 and Q5, so it is never mapped to anything). Q4 falls out of the table: a juz or hizb opens its start ayah's surah at that ayah.

`QuranReaderViewModel.open(_:)` applies a place in this order: select (if asked), `mushaf.show(page:)` (if there is a page), `separatedLocation = ayah`, then either `separatedSurah = ayah.surah` (another surah: the list is rebuilt and opens at `separatedLocation`) or a new `SeparatedScrollRequest` (the same surah: the list on screen scrolls). The location is written **before** the surah, because the surah is what re-evaluates the view that reads the location.

**The switch.** `QuranReaderViewModel.setDisplayMode(_:)` (and `toggleDisplayMode()`), ported from `ReaderModel.setDisplayMode`:

- separated → Mushaf: `mushaf.show(page: corpus.pageNumber(for: separatedLocation))`, the page holding the first ayah in view.
- Mushaf → separated: `separatedLocation = corpus.page(mushaf.page)?.firstAyah`, `separatedSurah = separatedLocation.surah`: the first ayah of the page on screen. The chrome request is cleared.
- Then `settings.select(displayMode:)`. The place is set first, so the new reader is built already positioned.
- A mode the build cannot show is refused before anything moves; in the Tanzil build the function is a no-op and writes nothing.

`location` (for M6 and the tests) is derived: the page's first ayah while pages are showing, else `separatedLocation`.

### 3.4 What must not be read in a `body`

M4 measured what happens when a page turn re-evaluates the pager's row of units (Mushaf 8.2: 49 s against 37 s paging 1→604). The reader screen sits above the pager, so the rule is strict:

- **`QuranReaderView.body` and its content subview read nothing that changes while reading**: not `mushaf.page`, not `mushaf.selectedAyah`, not `location`. They read the phase, `separatedSurah`, the scroll request, the display mode and the chrome request, all of which change at navigation rate.
- **`separatedLocation` is `@ObservationIgnored`**, on purpose. It is written on every top-ayah change and read in a body in exactly one place: the content subview passes it as the surface's `separatedAyah`, which `SeparatedReaderView` reads once when a list is created. A list is created for **three** reasons: `separatedSurah` changed, the view tree was rebuilt, or **the mode switched to separated**. The value wanted is the one current at that moment, so the content subview's body must run at each of the three, which means each is an *observed* read there: the phase, `separatedSurah`, and `showsMushafPages`. (As first written this note named two reasons and the content subview did not read the mode; a switch inside one surah then rebuilt the list from a stale place. Found in review, fixed before commit.)
- The navigation title is the surah's name in separated mode (changes with `separatedSurah`) and the section's title in Mushaf mode. It is **not** the surah of the current page: the page prints its own surah, juz and number, and a title that followed the page would re-evaluate the reader on every turn.

**M5.0's note on `SeparatedReaderView`** (its rows are re-evaluated whenever the top ayah changes): this design makes that **neither better nor worse**. The re-evaluation comes from the list's own `@State topAyah`, read in its `body` by `onChange`; that is inside M5.4's file and stays. What this design guarantees is that the report of the top ayah goes into an unobserved property, so nothing *above* the list is invalidated by scrolling. Had the view model published the location, the reader, the surface and the list would all have been re-evaluated per ayah scrolled: worse. The fix M5.0 named (a skippable row) is M5.4's.

### 3.5 The page unit (T11) and iPhone landscape

The reader feeds the pager **no size at all**, and that is the design. `MushafPagerView` measures its own `GeometryReader` and reads the size classes from its environment, so in a tab it is asked about the tab's area and in the split view about the detail column: a spread appears beside the sidebar only if one fits there, and closing the sidebar gives it more room with no code. What M5.1 must do is not get in the way:

- no `UIScreen`, no window size, no size passed down;
- nothing between the stack and the surface that ignores safe areas or fixes a frame;
- no reading of `mushaf.visiblePageCount` for layout.

iPhone landscape is `MushafPageUnit.resolve`'s rule 2 (compact height: one page fitted to the width, or a spread if the reader chose two pages), fed by `settings.phoneLandscape`. Unchanged. One consequence of living in Noor: an iPhone Plus or Pro Max in landscape has a *regular* width, so `MainInterfaceView` shows the sidebar arrangement and the page sits in the detail column, width-fitted. That is correct and needs no code; it is named in section 8 so nobody is surprised by it.

**Q5 (M5.6) is not made harder.** The Mac threshold is a new input to `MushafPageUnit.resolve`, evaluated in the pager from the same geometry. Nothing above the pager decides or caches the unit.

### 3.6 Keep-awake

Already applied by `QuranReadingSurface` (`.keepScreenAwake(settings.keepsScreenAwake)`), and that stays the only call site. Because the surface now lives inside the reader's destination, the scope is right without more code: it is on only in the `.ready` phase, it clears when the reader is popped, when another screen is pushed over it and when another tab is selected (`onDisappear`), and it is re-applied on return. Off unless `readerKeepsScreenAwake` was set; the row that sets it is M5.6's. M5.1 adds no second call and no key.

## 4. Navigation

### 4.1 `QuranRoute`, for the whole of M5

**Designed now, declared as each screen becomes real.** M5.1 declares one case. A case with no destination would need an arm in the `navigationDestination` switch that draws nothing, which is the dead button the owner ruled out, one level down. Adding a case later is additive: no payload below changes shape.

| Case | Payload | Declared in | Notes |
|---|---|---|---|
| `.reader` | none | **M5.1** | See below for why it carries no target. |
| `.search` | none | M5.5 | The query and results live on the search view model, so reopening search shows them. |
| `.surahInfo(Int)` | surah number | M5.2 | From a Library row. |
| `.tafsir(VerseReference)` | the ayah | M5.3 | The edition is panel state on the coordinator, not part of *what* is open. |
| `.bookmarks` | none | M6 | |

**Why `.reader` carries no target.** The reader's place changes with every page turn and every scroll. A route payload would be stale one second after the push, and the first time the view tree was rebuilt (an iPad crossing compact/regular) the reader would be rebuilt *from the route* and jump back to where it was opened. So the place lives on the view model, outside the view tree, and the route says only that the reader is open. This is `HadithCoordinator.scrollTarget`'s argument, stronger.

### 4.2 What is path and what is not

| State | Where | Kind |
|---|---|---|
| Which screens are pushed | `QuranCoordinator.path` | navigation |
| A target for the reader, before the corpus is loaded | `QuranReaderViewModel` (parked) | reader state; the coordinator keeps none |
| Page, selection, chrome request | `MushafReadingState` | reader state |
| Separated surah and place, load phase | `QuranReaderViewModel` | reader state |
| Display mode | `QuranReaderSettings` | preference |
| "This reader is the screen in front" | `@State` in `QuranReaderView` | view state, rightly lost with the view |

Coordinator state that later tasks add beside the path, **none of it declared now**: `sheet: QuranSheet?` (reader settings M5.6, the compact ayah panel M5.3, the note editor M6), the panel's ayah, section and edition and the inspector flag (M5.3, ported from Mushaf's `AppRouter`). A type with no cases yet is not declared, for the same reason an unreachable route is not.

### 4.3 `open(_:)` semantics

**One rule: the path holds at most one reader, and when it does the reader is `path[0]`.**

- `open(_ target: GoToTarget)`: **`reader.open(target)` first, then** the path becomes `[.reader]` (left alone if it already is). So from the root it pushes a reader whose first frame is already at the target; with the reader already on screen it **retargets in place and deepens nothing**, which is `HadithCoordinator.page(to:)`'s behaviour; from a screen pushed above or instead of the reader it replaces the stack with the reader.
- `openReader()`: the same without a target: the reader where it was left. For M5.2's Continue reading; M5.1's only caller is the DEBUG launch.
- `popToRoot()`: `path = []`.

The coordinator is built over the reader's view model (`init(reader:)`) and keeps no target of its own. **This replaced the first design**, in which `open` stored a one-shot `pendingTarget` that `QuranReaderView` consumed in `onChange(of:initial:)`. That ran after the reader's first body pass: the reader was built at its previous place (a throwaway list or font window, and a flash of the old place), and in separated mode with the surah unchanged the list's own initial jump could run after the new scroll request and leave the reader on the old ayah. Applying the place before the push removes the hand-off and the race with it. Found in review, fixed before commit.

Consequence for M5.5, stated so it is a choice and not a surprise: opening a search result replaces search with the reader, and the Library button then goes to the root. That is Mushaf's behaviour (search was a sheet that closed on a result), and the results are one tap away again because they live on the search view model. If M5.5 wants "back to results", it changes this one function, not the enum.

**The external routes** (`AppContainer+Routing`, tab selected first, as today):

| Route | Does | Reader already on screen |
|---|---|---|
| `AppRoute.quran` | `quranCoordinator.popToRoot()` | It is popped. Unchanged from today's `closeReading()`: the route has always meant "the Quran tab, at its list", and the list is where Continue reading will be. |
| `AppRoute.quranVerse(ref)` | `quranCoordinator.open(.ayah(ref))` | Retargeted in place, in the mode the reader is in; the ayah is selected so the reader can see which one was meant. |

A `ref` this corpus does not contain still *routes* (the tab is selected, the reader opens) and then moves nothing: the reader shows where it was. It never shows an empty surah. T7 holds: `.quranVerse(VerseReference)` is unchanged, and so are `DeepLink.quran` and the quick action, which go through `AppRoute.quran`.

`AppRoute` gains no case in M5.1. `.quranPage` comes with `DeepLink.quranPage` in M7 and will be `open(.page(n))`.

### 4.4 Back

**The reader hides the system back button and carries its own leading Library button**, which calls `popToRoot()`.

- The owner's toolbar list names Library, and in Noor the Library is the tab's root, so "Library" and "back" are one action. Two controls for it would be two doors to one room.
- The edge swipe that comes with the system back button starts at the same screen edge, in the same direction, as a page turn in the Mushaf pager: in an English interface the swipe to the next page begins at the left edge, and in an Arabic one the swipe to the previous page begins at the right. A paging scroll view inside a navigation stack is expected to lose that contest to the pop gesture. In Mushaf the reader was the window's root and had no pop gesture to lose to. **Unverified on device**; this is the conservative choice, and hiding the back button is also what removes the gesture. Section 7 has the check.
- A toolbar item declared by the reader can be tinted with a page colour. The system back button takes the stack's tint, which is the app's accent, and the app's amber on the sepia page is the washed-out combination `CLAUDE.md` already records.

The cost is real: no swipe-back in separated mode either, where no conflict exists. One back affordance in both modes is worth more than a gesture that works in one. Reversible in two lines; listed in the hand-back.

### 4.5 What is preserved

| Event | Preserved | Not preserved |
|---|---|---|
| Leaving the tab and coming back (tab bar) | Everything: path, page or scroll position, selection, mode. | Immersive: the bars are back. |
| A screen pushed over the reader, then popped | Everything. | Immersive. |
| iPad crossing compact/regular (the arrangement is rebuilt) | Path (coordinator), page (`MushafReadingState`; the pager re-anchors on it), separated surah and first ayah in view (`separatedLocation`, read when the new list is built), selection, mode. | The separated list's exact pixel offset: it reopens with the first visible ayah at the top. |
| Back to the root, then a surah row | The mode. | The place: a row is an explicit target. |
| Sidebar selection on iPad/Mac moving away and back | As "leaving the tab": the detail column is rebuilt from the same coordinator and view model. | Immersive (not available there anyway). |
| Relaunch | The display mode if the reader ever pressed the toggle, and every other reader preference. | Path, place, selection: **in memory only in M5.1.** The tab opens at its root and the reader at 1:1 until told otherwise. `ReadingPosition` is M6. |

### 4.6 Q3: the bars take the page's colours, and only there

**How chrome is styled today** (read before choosing): `ChromeTypography` sets *fonts only*, through the appearance proxies' attribute dictionaries, and deliberately installs no `UINavigationBarAppearance` so the system's own bar material survives; it leaves colour out of every dictionary, so a title's colour is whatever the bar's colour scheme gives it. `.themed(_:)` sets the environment's theme, the accent as `tint`, and `preferredColorScheme` from the appearance override, once at the root. `MainTabView` is a plain `TabView`. So nothing colours a bar today, and anything UIKit would be this app's first global bar appearance.

**The mechanism: SwiftUI's toolbar modifiers, emitted by the reader screen itself, and nothing global.**

```
.toolbarBackground(palette.background, for: <bars>)
.toolbarBackground(isActive ? .visible : .automatic, for: <bars>)
.toolbarColorScheme(isActive ? palette.colorScheme : nil, for: <bars>)
```

with `<bars>` = `.navigationBar, .tabBar` on iOS and `.windowToolbar` on macOS, chosen inside `QuranReaderChrome.swift`. `palette` is `theme.reading(settings.resolvedTheme(systemColorScheme:))`: the same function the surface calls, so the bars and the page cannot resolve differently. Colours reach the bars only through `ReadingPalette`, which reads `AppColor`'s Reader sets: no literal anywhere.

**Why it cannot leak.**

- These are preferences of the view that declares them. They are in force while that view is the top of the visible stack, and there is no app-wide state to forget to restore. That is the argument against `UINavigationBar.appearance()` and `UITabBar.appearance()`, which are global, do not update bars already on screen, and would have to be undone by hand on every way out of the reader.
- **Belt and braces: `isActive`.** `QuranReaderView` keeps `@State isOnScreen`, true between `onAppear` and `onDisappear`, and `isActive` is `isOnScreen` and the phase being `.ready`. When the reader is not the screen in front, the modifiers ask for `.automatic` and `nil`, so restoration is something the code says and not only something preference scoping implies.
- **No `preferredColorScheme` in the reader, ever.** It propagates *up* to the whole window: the sidebar, the other tabs and the status bar would all turn with the page. Mushaf could use it because the reader was the window. The surface already scopes `\.colorScheme` to the page's content with `.environment`, which goes down only.
- Toolbar items are tinted where they are declared (`QuranReaderToolbar(tint: palette.text)`), not through a `.tint` on the stack or the content, so no page colour reaches a view outside the bar. `palette.text` is used because `ReaderContrastTests` already holds it at AA on each page.

**Each way out.**

| Event | What restores the app's bars |
|---|---|
| Reader popped | The view is gone; its preferences with it. |
| Tab switched with the reader still on its stack | The tab bar follows the selected tab's content, and `onDisappear` sets `isActive` false. |
| A screen pushed over the reader | `onDisappear`, the same. |
| The app's accent or appearance changes underneath | The reader's `body` depends on `settings`, `\.colorScheme` and `\.theme`; it re-resolves the palette and re-emits. The page colours themselves are fixed per reader theme and do not move with the accent. |
| The reader theme changes (M5.6's sheet, over the reader) | `settings` is observed; the bars follow the page in the same update. |
| Loading or failed | `isActive` is false: the screen is an app-themed screen until there is a page to match. |

**Each arrangement.**

| Arrangement | Themed | Not themed |
|---|---|---|
| iPhone, tab bar | Navigation bar and tab bar. | The selected tab item keeps the app's accent (see the hand-back: the alternative needs a hook in `MainTabView`). |
| iPad compact (Slide Over, narrow Split View) | The same two bars. | |
| iPad regular, and an iPhone wide enough for the sidebar | The detail column's navigation bar. | The sidebar column, its bar and its list: untouched, they are not in the reader's subtree. |
| Mac | The window toolbar over the detail column, **if** the check in section 7 shows the sidebar's title-bar area is left alone; otherwise the Mac placement is removed and the Mac toolbar stays the system's. | The sidebar. |

**Unverified, and it matters:** on iOS 26 the bars are glass and the tab bar floats. Whether `toolbarBackground` paints them, tints them or is ignored there has not been seen. The design does not depend on the answer for *correctness*: the page's paper already extends behind both bars (`palette.background` ignores the safe area), so glass over the page takes the page's colour by being glass, and `toolbarColorScheme` keeps the glyphs legible on a dark page. It does depend on it for *appearance*, which is Saad's to judge from the screenshots.

### 4.7 Immersive mode

**State.** One stored flag, where M4 put it: `MushafReadingState.isChromeHidden`, toggled by the pager's `MushafTapHandling.toggleChrome`. It is a *request*. What the bars do is one pure question:

```
viewModel.isImmersive(voiceOverRunning:) =
    allowsImmersive && mushaf.isChromeHidden && showsMushafPages && !voiceOverRunning
```

`allowsImmersive` is injected at construction and defaults to `DeviceKind.isPhone`. The reader view adds `isOnScreen`. Every exit below is therefore true the instant its condition is, whether or not an `onChange` has run yet; the `onChange`s only clear the stored request so it does not come back later.

**The tap.** Unchanged from M4 and Mushaf, and not edited here. On an iPhone with VoiceOver off the pager hands its pages a `MushafTapHandling`: the outer 15% on each side turns the page; a tap on an ayah's words in the middle selects it (M5.3 opens the panel there); a tap in the middle *outside* the text (header, footer, margins, empty slots) shows or hides the chrome. Separated mode has no such area, its taps are row selections, and it has no immersive mode: the ruling is about the page regaining Mushaf's size, and Mushaf drops the request when the mode leaves Mushaf.

**What hides, on iPhone.**

| Bar | Modifier | Applied to |
|---|---|---|
| Navigation bar | `.toolbar(.hidden, for: .navigationBar)` | the reader view |
| Tab bar (T11) | `.toolbar(.hidden, for: .tabBar)` | the reader view |
| Status bar, home indicator | `.statusBarHidden(_:)`, `.persistentSystemOverlays(_:)` | **the section's `NavigationStack`**, through `quranSectionChrome` in `AppSectionView.quran` |

The last row follows Mushaf's own finding (`immersiveSystemOverlays`: "applied outside the navigation stack, where the status bar setting takes effect"). Whether one level out is enough inside a `TabView` is **unverified**; section 7 has the fallback. `.toolbar(_:for:)` is the iOS 16 spelling and the one that exists at iOS 17; `toolbarVisibility` is iOS 18.

The page grows when the bars go because the pager lays out against its safe area: that is the "regains Mushaf's size" of the ruling, and it is M4's geometry, not new code.

**iPad and Mac.** No immersive mode. The ruling says iPhone; the pager offers no tap handling there, and `allowsImmersive` makes the question false even if something set the flag. A tap selects an ayah and nothing else. On an iPhone in the sidebar arrangement (Plus or Pro Max, landscape) immersive hides the detail column's navigation bar and the status bar; there is no tab bar to hide, and the sidebar is the reader's own to close.

**How the bars come back.**

| Exit | Mechanism |
|---|---|
| A tap outside the text | The same toggle. |
| The reader leaves the screen: popped, covered by a push, another tab, a route from outside | `isOnScreen` is false at once; `onDisappear` calls `viewModel.exitImmersive()`. |
| The mode leaves Mushaf | `showsMushafPages` is false at once; `setDisplayMode` clears the request. |
| VoiceOver starts | The question is false at once; `onChange(of: accessibilityVoiceOverEnabled)` clears the request. |
| Relaunch | The request is in memory. |

**A sheet does not exit immersive.** The only sheet that can open while the bars are hidden is the ayah panel (M5.3), from a tap on the text, and bringing the bars back under it would resize the page and move the ayah that was just tapped. Mushaf keeps the request under its panel for that reason. M5.3 confirms this when the sheet exists; it is listed in the hand-back because the task text names a sheet as a candidate exit.

**VoiceOver is never trapped**, three ways: the pager gives no tap handling while it runs, so the mode cannot be entered; the question is false while it runs, so bars hidden a moment earlier are shown; and the request is cleared, so they do not hide again when it stops. Nothing here is gesture-only beyond what M4 shipped: the toggle is a plain tap.

**Platform glue.** All of the above that names an iOS-only placement or modifier is in `QuranReaderChrome.swift`. No view contains `#if os`.

### 4.8 `QuranLaunchOptions` without the debug reader

Three places, all `#if DEBUG`, all compiled out of Release:

1. **`AppContainer.init`**: as today, a launch with a reader target starts past onboarding on the Quran tab; it now also calls `quranCoordinator.openReader()` once every stored property is set, so the stack starts as `[.reader]`. New: `-quranData public` swaps the database before the repositories are built.
2. **`QuranLaunchHooks`**, a modifier on the reader destination in `AppSectionView` (where `.quranDebugEntry` is today). It sets `\.forcedRenderer` and `\.foldOverride`, and runs once per process, in this order, in one task: `await viewModel.load()`; `options.apply(to: settings)`; `viewModel.open(target)`; `viewModel.mushaf.select(options.selectedAyah)`; the immersive request; then the spread render or the page-through if asked.
3. **`QuranLaunchOptions`** itself: parsing only.

So the *path* goes through the coordinator and the *place* goes straight to the view model, in one ordered task. The place could have gone through `pendingTarget` too; it does not because the options that follow it (the selection) must run after it, and one task is an order where two hand-offs are a race.

The order in step 2 also fixes a latent fault: today the options are applied before the database has said what it can draw, so `-quranMode mushaf` is refused by `select(displayMode:)` and only *appears* to work because Mushaf is the default after `-quranResetSettings YES`. After the load, it is honoured.

| Option | Reaches | Meaning changed? |
|---|---|---|
| `-quranPage N` | `open(.page(N))` | No in the full build. In the Tanzil build it now moves nothing (it used to set a clamped page nobody could see); the visible result is the same, surah 1. |
| `-quranSurah N` | `open(.surah(N))` | No. |
| `-quranSurah N -quranAyah M` | `open(.ayah(N:M))` | No: `.ayah` selects, but the hook then sets the selection from `-quranSelect` (or clears it), so a capture has a band only when it asks for one, as before. |
| `-quranSelect S:A` | `viewModel.mushaf.select` | No. |
| `-quranMode`, `-quranTheme`, `-quranFollowSystem`, `-quranMarginMarkers`, `-quranFont`, `-quranTextSize`, `-quranResetSettings` | `apply(to:)`, now after capabilities are known | `-quranMode mushaf` is now honoured without a reset. In the Tanzil build it is refused, which is the point. |
| `-quranRenderer`, `-quranFold`, `-quranFoldHorizontal` | environment values set by the hook | No. |
| `-quranRenderSpread WxH` | `QuranSpreadRenderer.render` with `viewModel.mushaf` | No. |
| `-quranPageThrough`, `-quranPageThroughEvery` | `PerformanceProbe.pageThrough`, `show: viewModel.mushaf.show(page:)` | No. |
| **`-quranImmersive YES`** (new) | sets the chrome request, iPhone only | New. Mushaf had `-debugImmersive`. Without it an iPhone capture now includes Noor's two bars. |
| **`-quranData public`** (new) | the container opens `quran.sqlite` even where the full data is bundled | New. The database only: the packs and the registered faces stay what the bundle has, so it tests the capability gating, and a public clone remains the real check of the fallback (M5.7). |

**What every script should expect:** a capture is now the real reader, so it has a navigation bar and, on iPhone, a tab bar, and the page is smaller than in M4's captures unless `-quranImmersive YES` is passed. The scripts run unedited; whether they pass the new option is `ui-test-writer`'s call below.

## 8. Risks

**The plan's traps.**

- **T4 (two builds).** Mushaf mode is offered by one gate, fed from one call. A `.page` target is never translated into the Tanzil build: it resolves to `nil`. `-quranData public` makes the fallback testable where the full data is bundled, with the stated limit that packs and faces are still the bundle's.
- **T7 (routes keep working).** `AppRoute.quranVerse(VerseReference)` and `.quran` keep their cases and their meaning; `DeepLink.quran` and the quick action still reach the root. A reference the corpus lacks routes and moves nothing. `RecentActivity` end to end is M5.7.
- **T9 (no literal colours).** The bars are painted from `ReadingPalette` only.
- **T10 (strings).** Four literals, all with Mushaf's Arabic; one existing key reused; one key retired.
- **T11 (Noor is not full-screen).** The tab bar hides with the navigation bar. The pager is given no size, so it measures the tab or the detail column. No Mac command is added here. The trap has a third face the plan did not list, in 4.4: a reader that is *pushed* has a pop gesture, and Mushaf's never did.
- **T12 (fold).** The reader measures nothing; `FoldGeometry` stays with its one caller, the pager. The fold panel and tabletop are M7.
- **T13 (isolation).** The only work off the main actor is the repository's, by its own `@concurrent`. Nothing is detached; nothing new is `nonisolated` except value types and a pure function. Measurement and font registration are not touched.
- **T1, T16, T17.** Not in play: the pager still owns the font window; no tafsir; no search.

**Traps of this task's own.**

- **A page turn re-evaluating the reader.** Avoided by 3.4, and checked by the reviewer. `measure-performance.sh` is the regression test.
- **Bar colours leaking.** No global appearance, no `preferredColorScheme`, an explicit `isActive`, and a screenshot of the Home tab straight after a dark reader.
- **iOS 26 glass.** Unverified; correctness does not depend on it, appearance does. Screenshots go to Saad.
- **Dynamic tab bar hiding.** Toggling `.toolbar(.hidden, for: .tabBar)` on a screen already pushed has had rough edges across iOS versions. Check 3; no workaround is designed in advance.
- **A load cancelled by a view.** Avoided by the session-owned task.
- **A stale launch option.** `-quranMode mushaf` was silently refused before; applying after the load fixes it. Captures now include the bars: said in 4.8 so nobody compares an M5 capture with an M4 one and reads the difference as a rendering change.
- **The list losing its place when the tree is rebuilt.** Avoided: the new list is given the live location, read at build time.
- **An iPhone in the sidebar arrangement.** Plus and Pro Max in landscape. It works by the rules above; it is the least-tested combination and belongs on the device checklist.
- **Two readers of one view model.** Impossible by the path invariant; if a later task ever pushed a second `.reader`, both screens would show one state. The coordinator's comment says so.

**The two items M5.0 left on file.**

- **`DeepLinkInbox.makeCurrent` may run late for a cold-launch quick action.** Not fixed and not made worse. `AppContainer.init` gains one stored property that touches no disk and a DEBUG-only call, both placed without moving `makeCurrent`; nothing here sits on the scene-connection path, and the reader's target hand-off does not go through the inbox. The Quran quick action still posts `DeepLink.quran`, which is unaffected.
- **`SeparatedReaderView` re-evaluates its rows on every top-ayah change.** Neither better nor worse; see 3.4. The view model was shaped so that it cannot add to it.
