# M5.0 design: the silent-letter mark (Q1) and the launch crash (Q2)

Two independent fixes. Part A is on `quran-migration`; Part B is applied on `Development` as its own commit and merged in (the crash reproduced there: 0 of 20 idle launches, 1 of 40 under CPU load, `13f9272`).

**Correction, made when the tests first ran.** The note was written with 30 joined occurrences (3,958 free; alif joined 20, alif free 3,702). The implementation, which follows Unicode's joining table, found 27, and it was right: the measurement script counted any character in a letter category as joining, which took in U+06E5, the small waw, a modifier letter that joins nothing. Three alifs follow one (4:135 `تَلْوُۥٓا۟`, 18:16 `فَأْوُۥٓا۟`, 43:13 `لِتَسْتَوُۥا۟`) and stand free, because the letter before the small waw is a waw. The figures below are the corrected ones: 27 joined (alif 17, ya 10), 3,961 free (alif 3,705, waw 255, alif maqsura 1). The three words are named cases in `QuranTextFallbackTests`.

Status of the facts used here: everything under "Measured" was measured by the main agent and is not re-derived. Every verification step in section 7 has since been run by the main agent; the outcomes are recorded in place, with the date. (The rejected cascade remains untested on iOS, which is said where it is discussed.)

## 1. Goal and scope

**Part A.** Tanzil's U+06DF (the small circle over a letter that is written and not read) is drawn by KFGQPC Hafs as a large spacing dotted circle *after* its letter. Draw it correctly by setting the affected stretch of text in Amiri Quran, changing no character anywhere.

**Part B.** `BGTaskScheduler` launch-handler registration currently happens whenever SwiftUI first builds `AppContainer`, which is during scene connection and sometimes too late. Move the registration to the one callback that is before the end of launch by contract.

Out of scope, both parts:
- Any change to stored text, to `quran.sqlite`, to the builder, or to what copy, share, search, accessibility and `VerseReference` joins read.
- **The display-time substitution** (Tanzil U+0652 → U+06E1, U+06DF → U+0652). Not designed here. Saad's ruling: stop and ask first. The evidence is recorded in section 8 so the question is on file.
- The 37,148 Tanzil sukuns that Hafs draws with its round glyph instead of the Uthmani head-of-khah sukun. Font fallback cannot fix that; it is the same open question.
- Mushaf mode's Unicode path (see 3.A: it cannot be handed this text).
- Moving where `AppContainer` is built. Part B moves one call, not the container.

Later callers of the same one place: the ayah panel (M5.3), search results (M5.5), the widgets (M7). They call `QuranAyahText.attributed` and nothing else.

**The mechanism: explicit runs throughout, one rule for how long each run is.**

- A run is a stretch of the *displayed* `AttributedString` whose font is named as Amiri Quran. Everything else carries no font attribute and takes the reader's face from `readingFont(size:)` exactly as today.
- Where the base letter **stands free** (the letter before it does not join forward, and the base does not join the letter after it), the run is the one `Character` made of the base and its U+06DF. Measured: 3,961 of 3,988.
- Where the base **joins** on either side, the run is the **whole word**, so every join stays inside one face. Measured: 27 of 3,988.

Why this and not the alternatives:

| Option | Verdict |
|---|---|
| CoreText cascade (reduced character set + `[Amiri]`), `Font(ctFont)` | Rejected as the mechanism. It gives the right result for free-standing bases and the wrong one for joined bases (measured on three sample words, `مِا۟ئَةَ`, `أَفَإِي۟ن` and `بِأَيْي۟دٍ`, in both `CTLine` and SwiftUI `Text` on macOS; the mechanism is per cluster, so the same holds for all 27), so it can never be the only mechanism: runs are needed anyway. It also needs CoreText in the drawing path, a cached descriptor of a non-Sendable CF type, and it is unverified on iOS. |
| Whole-word runs for all 3,988 | Verified on macOS and never breaks a join, and it is the documented **fallback** below. Not the first choice because of how much text changes hand: a whole word in a lighter face with taller marks in 2,240 ayahs (36% of the Quran), against one alif or waw. Compare rows D and E of `q1-swiftui.png`: D is nearly indistinguishable from KFGQPC's own reference, E has a visibly foreign word. This is the same "patchwork" argument that rules fallback out for the sukuns, at one tenth the scale. It is also further from Saad's stated first choice, "per-character font fallback". |
| **Cluster runs where free, word runs where joined (chosen)** | The cascade's result for the 3,961 and the per-word result for the 27, with **one mechanism** (explicit runs) rather than two. The cluster run is the same run boundary CoreText's own fallback produced (`[Hafs …] [Amiri 0627 06DF] [Hafs …]`), declared instead of discovered. The cost is the joining rule: about forty lines, pure, and pinned by the measured counts. |

**Settled (2026-10-10).** When this note was written nobody had rendered explicit *cluster* runs, only the cascade (row B) and whole-word runs (row C), and `QuranTextFallback.usesClusterRuns` was made the **one decision in one file** in case they did not reproduce row B. They do. On macOS (`ImageRenderer`, `q1-cluster-runs.png`) a declared cluster run draws exactly like the cascade for free-standing bases, and the joined words set whole keep every join. On the iPhone SE simulator (iOS 18.6) in the real separated reader, with a public-clone copy of the app, 2:5 and 2:6 draw one letter in Amiri with a small anchored circle, and 3:144 and 51:47 draw the whole word with its joins intact, at the default size and at an accessibility size. `usesClusterRuns` stays `true`. **Not checked on an iOS 17 runtime**: none is installed; test (b) should be run on one before release. Screenshots: `Screenshots/quran-migration/M5/M5.0/` (git-ignored).

**Where it applies, and what it costs elsewhere.**

- Only when the reader's face is `.kfgqpcHafs` **and** the text contains U+06DF **and** Hafs registered (if Hafs did not register the words are already in a substitute face that draws the mark properly; naming Amiri runs inside it would be patching a problem that is not there).
- The full (QUL) build has no U+06DF. Its cost is one pass over the ayah's unicode scalars with no allocation, then the same `AttributedString(text)` the row builds today.
- With Amiri as the chosen face nothing is scanned at all.
- **Not per frame, but not free while scrolling either.** `paragraph` is computed when SwiftUI evaluates a row's `body`. That is where the marker's `AttributedString` was already built. It is not once per row: `SeparatedReaderView` reads the top ayah in its own `body` and hands each row a fresh closure, so the realised rows are re-evaluated whenever the top ayah changes, which happens during a scroll. That structure predates this task; what this task adds to each such evaluation, in the Tanzil build and only for an ayah holding the mark, is three scalar scans, one walk over the ayah's `Character`s, two small arrays and one range conversion per run. It has not been measured. No cache is added here; if it shows in a profile, the fix is to make the row skippable (a stable closure or `Equatable`), not to cache text. A Later item.

**Dynamic Type and leading.** The caller passes the size *already scaled* (`textSize × typeScale`, the product the row computes today for the marker). The fallback font is `ReaderFont.amiriQuran.font(size:)`, which is `Font.custom(_:fixedSize:)`, so nothing is scaled twice. `ReadingFontModifier` and the per-face line-spacing floors are not edited; the paragraph keeps the Hafs floor because Hafs is still its face.

**What reads the stored string, unchanged:** `.accessibilityValue(Text(verbatim: ayah.text))`, `onSelect(ayah.id)`, and everything outside the row. `QuranAyahText.attributed` receives the stored `String` and returns a value; it has no way to write anywhere.

### 3.B Part B

- `AppDelegate.application(_:didFinishLaunchingWithOptions:)` calls `BackgroundRefreshScheduler.registerLaunchHandler()`. No dependency is needed at that moment: registration needs only the identifier.
- `AppContainer.init` builds its `BackgroundRefreshScheduler` as today and, where it used to call `register()`, calls `BackgroundRefreshScheduler.makeCurrent(backgroundRefreshScheduler)` under the same `registersBackgroundRefresh` flag.
- When the system later runs the task, the handler hops to the main actor, reads `BackgroundRefreshScheduler.current` and calls its `run(_:)`. If no container has published one, it completes the task with `success: false`.
- `RootView.refillReminders()` still calls `container.backgroundRefreshScheduler.scheduleNextRefresh()`. Unchanged.

Ownership: `AppContainer` still owns the scheduler. The static only publishes which one is live, and only the composition root writes it. This is `DeepLinkInbox.current` again, for the same reason: UIKit constructs the delegate with no argument list. It is a **second** published static in a project that has said twice it wants one; that cost is real and is the price of not moving the container (see the alternatives in 5, Batch 2).

`registersBackgroundRefresh` keeps its name, its default and both test call sites. What it guards changes from "make a real system call" to "publish this container's scheduler as the one the launch handler runs", so a container built by a test, with a mock notification service, never becomes the target of the host app's handler. Registering twice is no longer possible at all: there is one call site and UIKit calls it once per process.

### Batch 1

**`Shared/Quran/Domain/QuranTextFallback.swift`** (new). Exact interface:

```swift
/// Which stretches of an ayah KFGQPC Hafs cannot draw, as ranges of the stored string.
nonisolated enum QuranTextFallback {
    /// U+06DF ARABIC SMALL HIGH ROUNDED ZERO: Tanzil's mark for a letter written and not read.
    static let mark: Unicode.Scalar = "\u{06DF}"

    /// The one decision: `true` draws a free-standing base as its own run, `false` sets every
    /// affected word whole. See docs/quran-migration/design/M5.0.md.
    static let usesClusterRuns = true

    nonisolated struct Occurrence: Equatable, Sendable {
        /// The `Character` carrying the mark: the base letter and its marks.
        let cluster: Range<String.Index>
        /// The whitespace-delimited word that contains it.
        let word: Range<String.Index>
        /// The first scalar of `cluster`.
        let base: Unicode.Scalar
        /// The base joins the letter before it or the letter after it.
        let isJoined: Bool
    }

    /// One pass, no allocation. `false` for every ayah of the full build.
    static func isNeeded(in text: String) -> Bool

    /// Every occurrence of `mark`, in order. Empty when `isNeeded` is false.
    static func occurrences(in text: String) -> [Occurrence]

    /// What to draw in the fallback face: ascending, non-overlapping, `Character`-aligned.
    static func ranges(in text: String) -> [Range<String.Index>]
}
```

Rules to implement:
- `isNeeded`: `text.unicodeScalars.contains(mark)`.
- A **word** is a maximal run of `Character`s that are not whitespace.
- An occurrence is a `Character` whose scalars contain `mark`. Its **neighbours** are the nearest `Character`s before and after it *inside the same word* whose first scalar is not a mark or format character (general category `Mn`, `Me`, `Cf`); `nil` at a word edge.
- `isJoined = (previous neighbour joins forward) || (base joins forward && next neighbour joins backward)`. A cluster whose first scalar is itself a mark (no letter to carry it) is treated as joined: the whole word is the safe answer.
- Joining follows Unicode `ArabicShaping.txt`, as a `switch` over `scalar.value` (no stored set, no allocation):
  - *Arabic letter*: U+0620...U+064A, U+066E...U+06D3, U+06D5, U+06EE, U+06EF, U+06FA...U+06FC, U+06FF.
  - *Non-joining* (joins neither way): anything that is not an Arabic letter, plus U+0621, U+0674.
  - *Right-joining* (does **not** join forward): U+0622...U+0625, U+0627, U+0629, U+062F...U+0632, U+0648, U+0671...U+0673, U+0675...U+0677, U+0688...U+0699, U+06C0, U+06C3...U+06CB, U+06CD, U+06CF, U+06D2, U+06D3, U+06D5, U+06EE, U+06EF.
  - Tatweel U+0640 joins both ways.
  - `joinsForward` = Arabic letter, not non-joining, not right-joining (or tatweel). `joinsBackward` = Arabic letter, not non-joining (or tatweel).
- `ranges`: group occurrences by word. If `usesClusterRuns` is false, or any occurrence in the word is joined, the word contributes its `word` range once; otherwise it contributes each occurrence's `cluster`.
- **The measured counts are the acceptance criterion** (section 7, test c). If the implementation's table is right the counts come out; the implementer cannot run them, so the table above is to be transcribed, not tuned. (As it turned out the table was right and one measured count was not; see the correction at the top of this note.)

**`Shared/Theming/UI/QuranAyahText.swift`** (new). Exact interface:

```swift
import SwiftUI

/// The one place that decides how an ayah's words are drawn.
nonisolated enum QuranAyahText {
    /// The face that draws what KFGQPC Hafs cannot.
    static let fallbackFace: ReaderFont = .amiriQuran

    /// `text`, character for character, with a font named only on the stretches `face` cannot
    /// draw. `scaledSize` is already scaled for Dynamic Type.
    static func attributed(
        _ text: String,
        face: ReaderFont,
        scaledSize: Double,
        hafsIsRegistered: Bool = true

```

Behaviour: start from `AttributedString(text)`. Return it untouched unless `face == .kfgqpcHafs`, `hafsIsRegistered`, and `QuranTextFallback.isNeeded(in: text)`. Otherwise, for each range from `QuranTextFallback.ranges(in: text)`, convert it with `Range<AttributedString.Index>(range, in: result)` and set `.font = fallbackFace.font(size: scaledSize)` on that slice. Set no other attribute. Never build the result from pieces: one `AttributedString(text)`, attributes applied in place, so the characters cannot differ from the input by construction. If that range initialiser is not available as written, convert by `Character` offsets over `result.characters`; do not invent an API.

The doc comment must state the rule in Saad's words: the stored text is never changed, only its drawing; copy, share, search and accessibility use the string this function was given, never its result.

### Batch 2

**Chosen fix: register from `AppDelegate.application(_:didFinishLaunchingWithOptions:)`.**

Why it is deterministic: `BGTaskScheduler`'s contract is that launch handlers are registered before the application finishes launching, and `didFinishLaunchingWithOptions` is that window by definition; it is where Apple's own documentation and sample put the call. UIKit calls it exactly once per process, before any scene is configured or connected (all five crash backtraces are in scene configuration or connection, i.e. after it). It does not depend on when SwiftUI evaluates a `@State` initial value, which is what turned out to vary. `@UIApplicationDelegateAdaptor` exists to deliver exactly this callback. The main agent should confirm the contract sentence in `BGTaskScheduler.h` when reviewing.

Alternatives considered:

| Option | Verdict |
|---|---|
| (1) Build the container in `ThawabForGodApp.init()` | Also before launch finishes (`App.main()` constructs the app before `runApp` enters `UIApplicationMain`, which the backtrace shows), and it needs no second static. Rejected for M5.0 because it moves about forty constructors to a new point in launch to fix the timing of one call, and it cannot be applied to both platforms: `AppContainer.init` ends in `menuBar.apply()`, which calls `NSApp.setActivationPolicy` (`MenuBarController.swift:72`), and whether `NSApp` exists inside `App.init()` cannot be shown from the code. So it would need the property declared two ways under `#if os`. Whether `State(initialValue:)` is still eager under the macro-based `@State` is also unknown; a plain `let` assigned in `init()` would avoid that question, at the cost of changing the property's kind. It stays on file as the answer if the two suspicions below turn out to be real. |
| (2) Register from the app delegate | **Chosen.** One call moves; nothing else changes timing; macOS is untouched by construction (`AppDelegate` and the scheduler are both `#if os(iOS)`). |
| (3) `willFinishLaunchingWithOptions` instead | Equivalent for the contract. `didFinish` is the documented place, so that one. |

## 7. Tests

### Part A, for `test-porter` (Swift Testing; new file `ThawabForGodTests/Quran/QuranTextFallbackTests.swift`)

Every test that needs Tanzil's text opens **`QuranTestData.publicDatabase`** explicitly, as `QuranFontCoverageTests` does, so it runs on the committed `quran.sqlite` even where the full data is bundled. Tests touching SwiftUI types need their own `import SwiftUI`; the CoreText ones `import CoreText` and call `FontRegistrar.registerBundledFonts()` first.

## 8. Risks

**Traps this task can hit.**

- **Quran text is never altered (the hard rule).** Avoided by construction: one `AttributedString(text)`, attributes applied in place, tests (a) and (b). The substitution is not implemented.
- **T13 (isolation, measurement off main).** Not hit. No measurement path changes and both new types are pure and `nonisolated`. Had the Mushaf Unicode path needed the fix, `PageMetricsCache`'s detached measurement would have had to measure mixed-face text; test (f) pins the reason it does not.
- **T4 (two builds).** The fix must be inert in the full build and the tests must still see Tanzil's text there: `isNeeded` is the gate, and every Tanzil test names `publicDatabase`.
- **T5 (widgets).** The widget registers Hafs from the App Group and has no Amiri. In M7 it either copies Amiri too and calls `QuranAyahText.attributed`, or draws its ayah in Amiri outright. Both files are in `Shared/` so either is open; M7's design decides.
- **T17 (search highlighting, M5.5).** Highlights are ranges over the displayed string. Because `attributed` preserves every character, a `Range<String.Index>` over `ayah.text` converts to the result with the same initialiser this design uses; M5.5 applies its highlight on top of the returned value rather than building its own string.
- **`Shared/` imports.** Kept to Foundation and SwiftUI by choosing runs over the cascade.
- **Dynamic Type squared.** Avoided: the size passed is already scaled and the font is `fixedSize:`.
- **Uneven line height** where a line carries an Amiri run: **confirmed** (2026-10-10). In 2:102 on the iPhone SE at the default size the gap above a line carrying the mark is about 157 px against about 125 px for its neighbours, and it is larger at an accessibility size (seen in the accessibility-size capture of 2:5: about 330 px above a line with the mark against about 230 px above one without). SwiftUI sizes a line by its tallest face and iOS 17 offers no per-run line height. Reported to Saad with the screenshots rather than tuned; it bears on the substitution question.
- **Cluster runs**: verified on macOS and iOS 18.6, see 3.A. Not checked on an iOS 17 runtime.
- **The joining table is transcribed, not derived by the implementer.** A wrong entry shows as a wrong count in test (c). The rule was that the expected numbers are never edited to match the code. **They were edited once**, and Saad is told so in the stop report: the first run gave 27 joined against an expected 30. The two rules were compared occurrence by occurrence, independently of the test; the three differences are alifs after U+06E5 (small waw, general category Lm, absent from `ArabicShaping.txt` and so non-joining), each preceded by a waw, which does not join forward. The implementation was right and the measurement script, which took any letter-category character for a joining one, was wrong. The three words are now named test cases, so the corrected expectation is pinned by the cases that distinguish the two rules, not only by a total.

**On file for Saad: the evidence for the substitution question (not designed, not implemented).**

- Counts in `text_hafs`. Committed Tanzil build: U+0652 × 37,148; U+06DF × 3,988 (in 2,240 ayahs); U+06E0 × 66; U+06E1 × 0. Full QUL/KFGQPC build: U+06E1 × 37,148; U+0652 × 3,988; U+06E0 × 66; U+06DF × 0.
- After mapping Tanzil's U+0652 → U+06E1 and U+06DF → U+0652, the sequence of these marks is identical in all 6,236 ayahs (41,202 marks compared). The two encodings are a permutation of each other: in KFGQPC's, U+0652 is the silent-letter circle and U+06E1 is the sukun; in Tanzil's, U+06DF is the silent-letter circle and U+0652 is the sukun.
- Glyphs: in Hafs, U+06DF is a spacing glyph (advance 704, no anchor); U+0652, U+06E0 and U+06E1 are zero-advance anchored marks. In Amiri Quran all four are anchored marks.
- **A consequence beyond the question Saad asked.** Today Hafs draws all 37,148 Tanzil sukuns with KFGQPC's round glyph, not the Uthmani head-of-khah sukun. This fallback does not touch that and cannot: 37,148 clusters in a second face is a patchwork. Only the substitution, or Amiri as the face, draws the public build's sukuns as the Madinah print does.
- Images: `…/scratchpad/fontlab/q1-options.png` (row 3 and row 7 are the substitution, row 8 the reference) and `q1-swiftui.png`.

**Part B: other work in `AppContainer.init` and whether it depended on running before the first scene connects.** Only what the code shows:

- `tipsService.configure()` (`:426`): **does not depend on it.** Its requirement is "before any view that carries a tip is built", and no such view can be built without the container, because `RootView` takes it as an argument. The comment stays true.
- `reachability.start()` (`:439`): **does not depend on it.** `isOnline` defaults to `true` and every update hops to the main actor.
- `DeepLinkInbox.makeCurrent(deepLinks)` (`:444`): **may depend on it; not shown either way.** `AppSceneDelegate.scene(_:willConnectTo:options:)` reads `DeepLinkInbox.current` to deliver a cold-launch quick action and drops the link when it is `nil` (`AppSceneDelegate.swift:91-93`). The crash reports show the container being built at two different points of scene connection (three in `configurationForConnecting`, two in SwiftUI's own `scene(_:willConnectTo:)`). If this project's delegate callback can run before the second of those, a cold-launch quick action is silently lost.
