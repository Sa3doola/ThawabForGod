# M6.4 — Reading position, Continue reading, Home card, RecentActivity, recent searches (lean)

## 1. Goal
- The reading position is written to SwiftData, debounced and off main. The Library's Continue reading bar and a new Home card read it after a relaunch. Each reader session leaves one `RecentActivity` Quran chip that opens the ayah. Search shows the last 10 searches, which can be cleared.
- Out of scope: publishing the position to the App Group or widgets (T5, M7), khatmah, Mac ⌘ shortcuts, M6.3's Bookmarks files (not touched), and a position per display mode.

## 3. Data flow
- **Who records:** `QuranReaderViewModel.noteLocationChange()` (private). It guards `corpus != nil`, sets `hasLivePlace = true`, then calls `positions?.recordReadingPosition(location)`. It is called at the end of a successful `open()`, `select()`, `separatedTopAyahDidChange()`, `setDisplayMode()`, and from `mushaf.onPageChange` **only while `showsMushafPages`** (in separated mode `open()` moves the page before `separatedLocation`). The VM sets `onPageChange = { [weak self] _ in … }` in `init`.
- **Debounce (in the store):** `recordReadingPosition` returns early if the ayah equals `readingPosition?.ayah`. Otherwise it updates memory now (`edit(rebuildsLists:false)`, as today), keeps `pendingPosition`, cancels and replaces a stored `positionTimer` Task that runs `Task.sleep(for: positionDebounce)` (default 1 s) and then enqueues the write on the existing chain. `flushReadingPosition()` cancels the timer, enqueues any pending position now, and then `await flush()`. This is the `ActivityRecorder` shape. **Why not `.task(id:)`:** the location is deliberately unobserved (M5.1 §3.4); observing it in a body would re-run the reader on every page turn.
- `hasReadingPosition`: a stored Bool, set from `readingPosition`'s `didSet` only when nil↔non-nil flips. The coordinator reads this, never `readingPosition`, so the Library does not re-run on page turns.
- **Session end:** `QuranReaderView` calls `viewModel.endSession()` (synchronous) in `.onDisappear` and on `.onChange(of: scenePhase)` when it becomes `.background`. `endSession()` stores `sessionEnd = Task { await positions?.flushReadingPosition(); activity?.record(.quran(location, of: surah.ayahCount, at: now())); await activity?.flush() }` and guards that the corpus and the surah exist. `awaitSessionEnd()` awaits it. One chip per kind, so each session replaces the Quran chip. Subject "s:v" (T7).
- **Library resume:** `QuranLibraryViewModel.resume`. If `reader.hasLivePlace`, it uses the current live path (unchanged). Otherwise it uses `userData?.readingPosition?.ayah`, guarded by `corpus.ayah(ref) != nil`, with `page = showsPages ? corpus.pageNumber(for:) : nil` (nil in Tanzil). `QuranLibraryView` is unchanged: it still reads `resume` only while `canContinueReading`.
- **Home:** `HomeViewModel.start()` replaces `async let activities` with one child that calls `await quranProgress?.settle()`, then `loadContinueReading()`, then `loadRecentActivities()`. Settling first avoids the pop-vs-reload race. `subject(of:)` `.quran` → `quranProgress?.surahName(ref.surah, in: .current())`. Home re-runs `start()` on every appearance (tab switch), so it is always fresh.
- `QuranHomeProgress`: `settle()` = `await reader.awaitSessionEnd(); await userData.flush()`. `lastReadAyah()` = the store's ayah, kept only if `verse ∈ 1...surah.ayahCount`. Surah names come from `reader.corpus` if it has loaded, else from `repository.surahs(style: MushafStyle.madaniV2.id)` read once and cached. **Home never loads the whole corpus.**
- **No position:** `continueReading == nil`, so `renderableSections` drops the card (the existing rule) and it is only listed in Customize. The Library bar is absent too.
- **Recent searches:** stored under `.quranRecentSearches` as a JSON `[String]`, newest first, unique by trimmed text, `prefix(10)`. Unreadable → `[]`. `clear()` writes `nil` (removes the key). They are remembered on `.onSubmit(of: .search)` and on a result tap (as in Mushaf `SearchView.remember()`), and never while typing.

## 4. Navigation
- No new `QuranRoute`. `QuranCoordinator(reader:search:userData: QuranUserDataStore? = nil)`.
- `canContinueReading = (hasShownReader || userData?.hasReadingPosition == true) && !path.contains(.reader)`. `hasShownReader` stays a private session flag and is no longer the bar's only source.
- `openReader()`: if `!reader.hasLivePlace`, `let ayah = userData?.readingPosition?.ayah` → `open(.resume(ayah))`, which takes back a rejected stale ayah on a cold launch. Otherwise `showReader()`. The Library bar already calls `openReader()`, so `QuranLibraryRows.swift` is unchanged.
- `AppRoute.quranContinue` → `router.selectedTab = .quran; quranCoordinator.openReader()`. The Home card uses it. The RecentActivity chip keeps `.quranVerse(ref)` (opens the ayah selected, M5.7 chain).
- No `DeepLink` change. Restore after a relaunch: the stack starts at the Library and the bar or card brings the reader back.

## 8. Risks
- **Page-turn invalidation (M5.1 §3.4):** the location stays unobserved. The store's `readingPosition` changes per turn, but the only observed reads are `hasReadingPosition` (flips once) and `resume` while the reader is off-stack.
- **Pop vs reload race (old CLAUDE.md lesson):** Home `settle()`s before reading. The Library uses the live place after a session.
- **Stale stored ayah:** `.resume` is resolved like `.ayah`. A coordinator take-back covers the cold launch, and the Library and Home guard `corpus.ayah` / `ayahCount`.
- **Recording the default 1:1 at launch:** nothing records until a corpus is loaded and a real navigation happens. `onPageChange` is ignored in separated mode.
- **Lost last second:** quitting a Mac app may skip `onDisappear`; at most `positionDebounce` (1 s) is lost. Accepted.
- **T7:** subject "s:v" and `.quranVerse` unchanged. **T5:** no App Group publish (M7). **T13:** chain and actor unchanged, no new detached work. **Tanzil:** pages are always nil-guarded through `showsPages`.
