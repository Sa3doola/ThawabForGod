# M8-B3: no tap-to-turn, and the turn that landed on the last page

## 1. Goal
- A tap on words always selects its ayah; a tap outside the text toggles the chrome (iPhone immersive) as before. Pages change only by swipe/scroll, plus keyboard and menu (M7.2) and Tabletop's buttons (M7.3).
- The programmatic turn path (`MushafReadingState.turn` → pager `onChange(of: state.page)`) can never land on the wrong page, and a stray scroll report can never write a far page into the reading state.
- Out of scope: the panel layout (B2), the B1 crash, VoiceOver paging, separated mode, any other key binding.

## Cause (from reading the code; not yet reproduced, see D1)
| Finding | Where |
|---|---|
| Why the **first word** turns: an RTL line starts at the right edge, so its first word sits in the right 15% `previousPage` zone (`MushafTapZone.zone`); the last word sits in the left `nextPage` zone. Only on iPhone (`DeviceKind.isPhone`) with VoiceOver off. | `MushafTapZones.swift:24-29`, `JustifiedLine.swift:43-46, 78-82` |
| No page-number/index mix-up: unit ids are page numbers (`stride(from: 1, through: 604, by: pageCount)`), `unitStart` and `turn` are right for 1/2 pages. | `MushafPagerView.swift:194`, `MushafPageUnit.swift:64`, `MushafReadingState.swift:46-63` |
| The real hazard is the RTL scroll view. Its origin is mirrored, so content offset 0 is the **last** unit (604, or 603 in spreads). One programmatic turn drives two scroll requests (`proxy.scrollTo` **and** `visibleUnit = target`, same transaction, inside the tap's gesture). If either one resolves in unmirrored offsets or the lazy row resets its offset, the view settles on the far end. | `MushafPagerView.swift:110-124` |
| Nothing catches it: `onChange(of: visibleUnit)` passes any reported id to `state.show(page:)` once the 500 ms `jumpTarget` window is over, and nothing re-checks after the window. So the screen and then the saved reading position become 604. A paging swipe can only move one unit, so a report more than one unit away that is not a jump target is always stray. | `MushafPagerView.swift:101-106, 120-123` |
| The tests hid it: `turnOnePage` taps the edge on iPhone and accepts *any* footer change, then tries the other way too. | `QuranUITestSupport.swift:323-359` |

## 3. Data flow
- Page truth stays `MushafReadingState.page` (owned by `QuranReaderViewModel`); the pager's `visibleUnit` is a mirror of it.
- Reports from the scroll view go in only through `MushafPagerStep.accepts`; a rejected one makes the pager scroll back to `unitStart(state.page)`. Programmatic turns use one scroll path, and the pager checks once more after it settles.
- No new `SettingsKey`, repository or container change.

## 4. Navigation
- No `QuranCoordinator`, `AppRoute` or `DeepLink` change. Restore is unchanged (`.task(id: unit)` re-anchors on rotation and fold changes); the new guard also protects that path from a mirrored landing.

## 8. Risks
| Trap | Avoidance |
|---|---|
| RTL mirroring (pager always RTL, lines pinned LTR) | No geometry decides behaviour any more; `accepts` rejects mirrored-origin reports. |
| Pager perf (M5.1, Mushaf 8.2) | Toggle stays one env value on the row; `MushafUnitView` gets no new inputs a turn changes. |
| `accepts` too strict for a Mac trackpad fling | Paging moves one unit per gesture; checklist 4 and B3(b) cover it. If a fling ever moves two, widen to 2 units (D2). |
| Guard loop (reject → scroll → stray again) | The re-scroll sets `jumpTarget`, so its own report is accepted; at most one retry per window. |
| Tests that accept any change | B3 asserts exact page numbers. |

## Decisions for Saad
- **D1:** The "last page" cause is inferred from the code, not reproduced. Recommendation: before B1, the implementer runs B3(a) on page 2 at HEAD with a temporary `print` of every `visibleUnit` report, and records which call reported 604 in the commit message. The fix holds either way.
- **D2:** A stray report is anything more than one unit away. Recommendation: keep one unit; widen only if a test proves a legitimate two-unit report.
