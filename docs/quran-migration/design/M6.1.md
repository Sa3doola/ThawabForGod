# M6.1 — Quran user data: models + repositories (lean)

## 1. Goal
- Persist bookmarks, notes, highlights (one per ayah each) and the single reading position in `PersistenceController`'s store, through one `@ModelActor` repository, and expose a `@MainActor @Observable QuranUserDataStore` that the M6.2–M6.4 UI reads synchronously per ayah.
- Out of scope: any UI, the bookmark toggle and highlight drawing (M6.2), the Library list (M6.3), debounce, Home card, `RecentActivity` and recent searches (M6.4), backup/merge, khatmah, legacy-bookmark migration.

| `QuranUserDataStore` | `Features/Quran/QuranUserDataStore.swift` | `@MainActor @Observable final class` | views ask per ayah while drawing (MAPPING concept map, "user data") |

- Boundary crossings: `QuranUserMarks` / `QuranReadingPosition?` actor → main; `VerseReference`, `HighlightColor`, `String`, `Date` main → actor. No `@Model` crosses.
- Records: every property has a default (`surah: Int = 0`, `verse: Int = 0`, `createdAt/updatedAt: Date = .distantPast`, `text = ""`, `colorRaw = ""`); no relationships, no `@Attribute(.unique)`, no `#Unique`/`#Index`. Identity = `(surah, verse)` as two `Int` columns (Hadith's triple, sortable in Mushaf order, `#Predicate` on lifted locals).
- Highlight colour stored as `HighlightColor.rawValue` (`Shared/Theming/Domain/HighlightColor.swift`, raw values are a contract); a row with an unknown raw value is skipped on read, not deleted. Drawing resolves with `ReadingPalette.highlight(_:)`; no `Color` is stored anywhere.

## 3. Data flow
- `AppContainer` builds one `QuranUserDataRepository(modelContainer: persistence.container)` and one `QuranUserDataStore(repository:positions:)` (same actor passed twice); exposes `let quranUserData: QuranUserDataStore`. No feature sees the actor.
- Store owns the in-memory truth: arrays (lists) + dictionaries `[VerseReference: …]` (lookups), loaded once at launch via `load()` (all marks, Mushaf measured 6,000 items ≈110 ms, off main here).
- Writes: optimistic in memory first, then one link appended to a serial write chain (`pending = Task { [previous = pending] in await previous?.value; try? await … }`), so writes reach the actor in tap order. `load()` is the chain head.
- Edits made before the load lands are kept in `pendingEdits` and re-applied to memory after the load assigns (the load read the disk before them). Write failure → log (`Logger`, category "QuranUserData") and reload from the repository; no user-facing error (Mushaf behaviour).
- Repository rules (ported from `SwiftDataUserDataRepository`): bookmark set when present = no-op (keeps `createdAt`); note text trimmed, empty deletes, unchanged = no-op (no `updatedAt` bump); same highlight colour = no-op, `nil` deletes; every write fetches all rows for the ayah, updates the first, deletes the rest; `marks()` keeps the newest row per ayah and deletes duplicates before returning. Position: one row, update in place, extras deleted.
- Clock: store's `now: () -> Date` (default `Date.init`) stamps every write; repository takes the date as a parameter.
- Position stores the ayah only, never a page: the page is resolved per corpus (`QuranReaderPlace.resolve(.ayah)`), so a full-build page number never reaches the Tanzil build (T4).
- No view touches SwiftData; `SettingsStore` is not used in M6.1.

## 7. Saad's manual checklist (no UI yet; full coverage is in the M6.2–M6.4 checklists)
1. iPhone, full data, existing dev install with tasbih counts and hadith bookmarks: install over it, launch → no crash; tasbih and hadith bookmarks still there (lightweight migration added four empty tables).
2. iPhone, full data, `-quranSeedUserData YES`: console prints `5 bookmarks, 3 notes, 6 highlights`.
3. Kill and relaunch with **no flags**: still `5 / 3 / 6` (the count is logged on every DEBUG launch, so this proves the disk, not the seed). Relaunch once more with the seed flag: still `5 / 3 / 6` (uniqueness per ayah).
4. `-quranResetUserData YES`: prints `0 / 0 / 0`; relaunch with no flags: still `0 / 0 / 0`. With both flags together: `5 / 3 / 6`.
5. iPhone, `-quranData public` + seed: same `5 / 3 / 6` (user data does not depend on the corpus).
6. Mac (`platform=macOS`), full data: steps 2–3.
- Reviewer acceptance: Domain file imports Foundation only; no `@Model` in any signature outside `Data/UserData`; schema lists the four records; no `@Attribute(.unique)`/`#Unique`; every record property defaulted; colour persisted as raw `String`; no `Color` stored; no new `L10nKey`; no `project.pbxproj` change; DEBUG code compiled out of Release; writes are chained, not fire-and-forget unordered `Task`s.

## 8. Risks
| Trap | Avoided by |
|---|---|
| T4 Tanzil fallback | position is an ayah, not a page; marks key on `VerseReference`, valid in both builds; nothing hidden needed (no UI) |
| T7 identity | `VerseReference` (two Int columns) is the identity; `description` "s:v" unchanged |
| T9 colours | raw value stored, resolved only by `ReadingPalette.highlight(_:)` |
| T10 strings | none added |
| Entity-name collision | records named `Ayah*Record` / `QuranReadingPositionRecord`, never the M3-deleted `QuranBookmarkRecord` / `ReadingPositionRecord`, so inference cannot map new entities onto stale tables on a device not launched since M3 |
| Migration failure | no `VersionedSchema`: SwiftData infers a lightweight migration on open (added entities → new empty tables; removed entities → dropped with rows; added attributes need defaults). If inference ever fails, `makeDefault()` is fatal → delete and reinstall the dev app (loses all local user data) |
| Stale ayah (M5.7) | a mark on an ayah the corpus lacks is kept and simply never drawn; M6.3 must render such rows without moving the reader |
| `@ModelActor` built on main | existing Hadith/Tasbih pattern; known iOS 17 quirk that work may run on main; acceptable at this data size, not changed here |
| Redraw (M6.2) | pages call `marks` closures; M6.2 must make sure a Canvas-drawn page observes the store's dictionaries (read them in `body`) |
