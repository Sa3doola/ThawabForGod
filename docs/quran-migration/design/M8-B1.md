# M8-B1: crash when leaving the open reader for another section

## 1. Goal
Leaving the Quran section with the reader (or any Quran push) on its path must never crash, in the sidebar or the tab bar, and every section must come back where it was left.
Out of scope: B2 (Mac surah tap, see Risks), B3-B5, any change to `QuranCoordinator`'s typed API, the Settings scene's own stack on macOS.

## Root cause (from the reports + code)
| Report | Device / runtime | Frames | Meaning |
|---|---|---|---|
| -175131 | iPad Pro 13 (M4), iOS 18.6 sim | `swift_unexpectedError` < `NavigationColumnState.boundPathChange(to:environment:)` < `NavigationAuthority.flushRequestQueue` | a `try!` inside SwiftUI's path comparison threw |
| -180436 | iPhone Duo, iOS 27.1 sim | same | same |
| -182621 | iPhone Duo, iOS 27.1 sim | `EnvironmentValues.subscript.getter` (keypath) < `EnvironmentBox.update` < `NavigationStackCoordinator.setViewControllers` < `_UIWindowSceneGeometrySettingsDiffAction` | a scene geometry change (fold/rotate) rebuilt a stack's hosted screens; an `@Environment(X.self)` read found nothing |

- Both crashing devices are at **regular width, so `MainSplitView`**, not `MainTabView` (the existing `testAnotherTabAndBackKeepsTheReader` covers the tab bar and passes).
- The split view's **detail column owns one `NavigationColumnState`** and adopts whatever `NavigationStack` is its content. `.id(router.selectedTab)` (`MainSplitView.swift:48`) gives the *stack* a new identity but not the *column*: the column keeps the last bound path.
- The sections bind **different path types**: Home `NavigationPath`, Settings `NavigationPath`, Adhkar none (internal), Quran `[QuranRoute]`, Hadith `[HadithRoute]`.
- With the reader open the column holds a non-empty `[QuranRoute]`; selecting Home/Settings binds a `NavigationPath`; `boundPathChange` compares them, throws `AnyNavigationPath.Error.comparisonTypeMismatch`, and the `try!` traps. The `.id` "fix" was only ever exercised with empty paths, where nothing is compared element by element (inference; confirm with the console line in check 7.1).
- Not the cause (checked): M7.2 key responder / `focusedSceneValue` (no path writes), M7.3 bottom panel (no path writes), M5.1 chrome (toolbar preferences only), reader `onDisappear` (`endSession`, `endBottomPanel`, `exitImmersive`: no path writes). No `NavigationLink(value:)` exists anywhere, so every push goes through a coordinator.

## 3. Data flow
- Paths still live on the coordinators (`AppContainer.quranCoordinator`, `.hadithCoordinator`); the view gets an erased view of them.
- get: `NavigationPath(wrappedValue)`. set: SwiftUI only ever **pops** (Back, swipe, tab re-tap, `.escape`), so truncate: keep `prefix(newPath.count)`; a longer path is ignored (cannot happen: no value links). Use the `set: { value, transaction in }` form and `withTransaction` so pop animations survive.
- Result: every stack the detail column ever sees is bound to a `NavigationPath`, so the column compares like with like.

## 4. Navigation
- No `QuranRoute` / `HadithRoute` / `AppRoute` / `DeepLink` changes. `navigationDestination(for:)` resolves typed elements out of a `NavigationPath` as before.
- `.id(router.selectedTab)` stays (fresh destination registrations per section); its comment is rewritten to name the real mechanism.
- Back/restore: unchanged; a section switch keeps every path on its coordinator.

## 8. Risks
- Inferred cause: if check 7.1 shows a different error, stop and re-design before batch B lands.
- Report -182621 (env assertion on a geometry change) may be a separate SwiftUI bug in the TabView <-> split view swap; if 7.4 still crashes after A, it becomes B1b (see Decisions).
- B2 (Mac surah tap does nothing) runs in the same detail column; re-test it after A, it may share this cause.
- Setter truncation would drop a SwiftUI-initiated push; none exist today. Any future `NavigationLink(value:)` in these sections must go through the coordinator instead (comment in the adapter).
- T11 (Quran in a tab / detail column): unchanged; chrome and focused-section commands are untouched.
- T13: adapter is main-actor SwiftUI glue; no new concurrency.
- Quran text, data files, Tanzil fallback, offline: untouched.

## Decisions for Saad
1. Fix shape: **adapter (recommended)**; alternatives were turning both coordinators into `NavigationPath` (loses `path.last == .reader`) or `.id` on the whole `NavigationSplitView` (rebuilds the sidebar on every tap).
2. Report -182621: treat as B1b only if 7.4 still crashes after A (recommended), rather than adding speculative environment re-injection now.
3. The bug lists plain iPhone, but the only logs are iPad and Duo. If it crashed on a portrait iPhone (tab bar), please attach that `.ips`; the design assumes it was a regular-width device.

## As shipped (supersedes §4, §5 and Decision 1 where they differ)
- The adapter (`Binding.navigationPath(isActive:)`) is kept so every stack shares one path type, but it is not what fixed the crash. Its setter only trims, and ignores writes from a section that is not selected (a torn-down stack reports an empty path).
- The fix that held is `.id(selectedTab)` on the **whole** `NavigationSplitView` (not the detail): with the id on the detail alone, a Hadith push followed by a switch to Quran left a blank pushed page in the column (accessibility dump, iPad Pro 13 M5, iOS 27.0). This is the alternative Decision 1 rejected; its costs are the sidebar being rebuilt per selection: dragged sidebar width resets, Mac sidebar keyboard focus, toolbar flicker. **Manual check on iPad and Mac:** sidebar width kept, arrow keys and ⌘1…⌘4, double-tap on a tab to pop to root.
- A 600 ms "settle window" after a switch was tried and removed: it hid real pops (double-tap on a tab).
- Regression test: `QuranSectionSwitchTests`, passing on iPad Pro 13 M5 (iOS 27.0), iPhone Air (tab bar) and iPhone Duo (side tab bar in landscape). Not run on iOS 18.6 or macOS yet.
